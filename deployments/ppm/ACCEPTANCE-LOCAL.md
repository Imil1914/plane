# Локальный стенд приёмки PPM 1.0 RC

Стенд для проверки по чек-листу приёмки владельца («Чек-лист приёмки владельца — PPM 1.0 RC»). Он работает на этом
Mac и открывается только с него: порты слушают на `127.0.0.1`, снаружи стенд не виден.

- Сборка — из тега `ppm-1.0.0-rc.2` (коммит `a9db1a118a`). Релиз `1.0.0-rc.2`, проект Docker Compose `ppm-accept`.
  Стенд обновлён с RC.1 на месте (2026-09-29): данные и учётки сохранились, добавлен Git-сервер (п. 6).
- Данные — синтетические: демо-пространство ROBOT/BIO и тестовые учётки. Реальных людей и паролей здесь нет.
- Команды ниже выполняются в Терминале из каталога `plane-fork/deployments/ppm`:
  ```bash
  cd ~/Desktop/PPM/plane-fork/deployments/ppm
  ```

## 1. Адрес и предупреждение браузера

Откройте **https://ppm-accept.localhost:18443** — лучше в Chrome или Firefox.

При первом входе браузер покажет предупреждение о сертификате: «Подключение не защищено» (Chrome) или «Предупреждение:
вероятная угроза безопасности» (Firefox). Для этого стенда это нормально. Сертификат выдал локальный центр
сертификации самого стенда (Caddy), а не публичный, поэтому браузер его не знает. Соединение при этом зашифровано.

- **Chrome:** «Дополнительные» → «Перейти на сайт ppm-accept.localhost (небезопасно)».
- **Firefox:** «Дополнительно…» → «Принять риск и продолжить».
- **Safari:** «Показать подробности» → «посетить этот веб-сайт», затем подтвердите паролем Mac.

Браузер запоминает это решение, повторять его обычно не нужно.

## 2. Учётные записи

Файл с учётками:

```
~/Desktop/PPM/plane-fork/deployments/ppm/.runtime/ppm-accept/acceptance-credentials.txt
```

- Открыть: `open -e .runtime/ppm-accept/acceptance-credentials.txt` (TextEdit) или `cat` в Терминале.
- В файле шесть тестовых учёток: роль, e-mail, пароль и для чего она нужна. Пароли сгенерированы автоматически и
  действуют **только на этом стенде**.
- **Файл никому не пересылайте**, не вставляйте пароли в чаты, задачи и письма. Он лежит вне Git (`.runtime/`
  исключён), права — только ваш пользователь (600), и удаляется вместе со стендом (п. 5).

| Учётка (роль в файле) | Кто это на стенде                                           | Для каких блоков чек-листа                                                                                                   |
| --------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `OWNER`               | руководитель проекта ROBOT, администратор демо-пространства | ваша основная учётка: «Перед началом», блоки 1–5, 7, 8                                                                       |
| `ROBOT_MEMBER`        | участник ROBOT                                              | второй вход для совместной работы — блок 1, п. 7 (в окне инкогнито или другом браузере); блок 6, п. 3 (отказ в `/ppm-admin`) |
| `ROBOT_VIEWER`        | наблюдатель ROBOT                                           | блок 1, п. 8: всё видно, редактировать нельзя                                                                                |
| `BIO_MEMBER`          | участник BIO, без доступа к ROBOT                           | блок 1, п. 9 (изоляция: прямая ссылка на доску ROBOT → отказ); блок 4 (поиск видит только BIO)                               |
| `OUTSIDER`            | участник пространства без доступа к проектам                | изоляция (блок 1, п. 9) — дополнительная проверка                                                                            |
| `ADMIN`               | администратор инстанса и глобальный администратор PPM       | блок 6: «Центр администратора», вход в чужой проект с баннером «режим администратора»; страница `/god-mode/`                 |

Что уже есть в демо-пространстве «PPM демо ROBOT/BIO»:

- проекты **ROBOT** и **BIO**;
- спринт, направления и задачи с исполнителями;
- доски Холста, файлы и заметки Хранилища, индекс «Мозга проекта».

У `ADMIN` есть ещё служебное пространство `ppm-rc-…`: его создала автоматическая проверка стенда (смоук), в приёмке
его можно не трогать.

Ограничения локального стенда:

- **Git (блоки 5 и 9).** GitHub App здесь не подключён, зато есть **свой Git-сервер** (п. 6): через него раздел «Код»
  проверяется полностью. Кнопки записи в Git (ветка и черновой PR из задачи) на стенде выключены — они объясняют
  это и не падают с ошибкой.
- **Почта не настроена.** Вход по ссылке, письма и «Забыли пароль» здесь не работают — это ожидаемо. Входите по
  паролю из файла.

## 3. Остановить и запустить

- Остановить (все данные сохраняются):
  ```bash
  ./ppm-deploy.sh --env-file .runtime/ppm-accept.env stop
  ```
- Запустить снова. Занимает 1–3 минуты и заканчивается строкой `ppm-accept is up at https://ppm-accept.localhost:18443`:
  ```bash
  ./ppm-deploy.sh --env-file .runtime/ppm-accept.env up
  ```
- Посмотреть состояние (все сервисы должны быть `healthy`):
  ```bash
  ./ppm-deploy.sh --env-file .runtime/ppm-accept.env status
  ```

После перезапуска Mac или Docker Desktop стенд поднимается сам, если перед этим его не остановили командой `stop`.

## 4. Если что-то не так

- **Страница не открывается.** Проверьте, что запущен Docker Desktop, и выполните `status`, затем `up` (п. 3).
- **Работает, но с ошибками.** Выполните проверку зависимостей:
  ```bash
  ./ppm-deploy.sh --env-file .runtime/ppm-accept.env preflight
  ```
  Все пункты должны быть `ok`.
- **Нужны журналы** (секреты в них скрыты):
  ```bash
  ./ppm-deploy.sh --env-file .runtime/ppm-accept.env logs api
  ```
- Запишите замечание в чек-лист и продолжайте. Чинить ничего не нужно.

## 5. Удалить стенд после приёмки

Удаление безопасно: `destroy` удаляет **только этот локальный проект**. Он откажет, если:

- в файле указан не локальный домен (не `*.localhost`);
- в файле указано боевое имя проекта `ppm`;
- контейнеры проекта обслуживают другой домен;
- имя проекта не набрано ещё раз.

Контейнеры разработки `plane-fork-*` — это другой проект, их удаление не затрагивает.

```bash
./ppm-deploy.sh --env-file .runtime/ppm-accept.env destroy --confirm-project ppm-accept
rm -rf .runtime/ppm-accept .runtime/ppm-accept.env .runtime/ppm-accept.backup-passphrase .runtime/ppm-accept-backups
docker image rm $(docker images --format '{{.Repository}}:{{.Tag}}' | grep '^ppm-accept/')
```

1. Первая команда удаляет контейнеры и данные стенда.
2. Вторая — файл учёток и настройки стенда.
3. Третья — образы стенда (~4,5 ГБ).
4. Если настраивали git по п. 6 — уберите доверие к сертификату стенда:
   `git config --global --unset http."https://git.ppm-accept.localhost:18443/".sslCAInfo`.

## 6. Git-сервер: выложить свой проект

Git-сервер стенда (Forgejo) открывается по адресу **https://git.ppm-accept.localhost:18443**. Браузер покажет то же
предупреждение о сертификате, что и для PPM (п. 1) — примите его так же.

**Вход администратора Git-сервера.** Учётка `owner`, одноразовый пароль — в файле (только для вас, права 600):

```bash
open -e .runtime/ppm-accept/forgejo-admin-credentials.txt
```

Войдите — Forgejo сразу попросит придумать свой пароль (не короче 12 символов). После этого удалите файл:
`rm .runtime/ppm-accept/forgejo-admin-credentials.txt`. Учётки Git-сервера пока отдельные от PPM: людей заводит
администратор Forgejo (RUNBOOK §17.5); единый вход «Войти через PPM» — следующая доработка (G2.2).

**Выложить проект — 5 шагов:**

1. **Репозиторий.** В Forgejo: «+» (справа вверху) → «Создать организацию», например `robot` → затем «+» →
   «Создать репозиторий»: владелец — организация, имя — как у проекта. README и .gitignore **не** добавляйте (иначе
   первый push попросит слить истории). Репозиторий по умолчанию закрытый.
2. **Токен вместо пароля для git.** Аватар → «Настройки» → «Приложения» → «Создать новый токен»: имя `Mac`, в
   «Доступ к репозиториям и организациям» — «Все (публичные, приватные и ограниченные)», в правах у `repository` —
   «Чтение и запись» → «Создать токен». Скопируйте токен сразу — Forgejo покажет его один раз.
3. **Один раз — доверие к сертификату стенда для git** (в Терминале):
   ```bash
   git config --global http."https://git.ppm-accept.localhost:18443/".sslCAInfo ~/Desktop/PPM/plane-fork/deployments/ppm/.runtime/ppm-accept/stand-root-ca.crt
   ```
   Это открытый сертификат центра стенда, не секрет; настройка касается только адреса стенда.
4. **Отправить код.** В папке проекта (если это ещё не git-репозиторий — сначала `git init`, `git add .`,
   `git commit -m "Первый коммит"`):
   ```bash
   git remote add stand https://git.ppm-accept.localhost:18443/robot/<имя-репозитория>.git
   git push stand --all
   ```
   git спросит имя — `owner`, пароль — **вставьте токен** из шага 2. macOS запомнит его в Связке ключей.
   Подмодули (если есть) выкладываются отдельными репозиториями.
5. **Подключить к проекту PPM.** Войдите в PPM под `ADMIN` (подключает только глобальный администратор PPM) →
   проект ROBOT → «Код» → «Подключить с нашего Git-сервера» → выберите репозиторий → «Подключить».

**Что проверить.** Сделайте коммит с ключом задачи в начале сообщения, например `ROBOT-7: собрал статьи` и
`git push stand` — через несколько секунд коммит появится в «Коде» проекта и в блоке «Код» у задачи ROBOT-7.
Запрос на слияние (PR) из ветки с ключом в названии (`ROBOT-7/stati`) тоже привяжется и покажет статус
«Открыт» / «Слит». Под `OWNER` видна кнопка «Как скачать код» с командами `git clone`.

**SSH вместо токена** (для тех, у кого есть SSH-ключ): «Настройки» → «Ключи SSH / GPG» → «Добавить ключ», адрес
`ssh://git@git.ppm-accept.localhost:2222/robot/<имя-репозитория>.git`.

С Windows веб-интерфейс Git-сервера открывается так же, как PPM (через тот же проброс порта), по адресу
https://git.ppm-accept.localhost:18443.
