# PPM — развёртывание и эксплуатация (release candidate)

Инструкция для сервера с одним доменом по HTTPS. Всё, кроме первого администратора и решений из п. 8, делает
оператор. Шаги **владельца** помечены. Команды выполняются из каталога `/opt/ppm/plane-fork/deployments/ppm/`.

> Все шаги отрепетированы локально (Caddy с локальным CA вместо Let's Encrypt, домены `*.localhost`).
> Протокол и измеренные времена — `.superpowers/sdd/2026-09-26-ppm-rc/task-RCA-report.md`.

Порядок первого развёртывания: **закрыто → администратор → открыто → стоп-условия → люди**.

1. Сервер, исходники, сборка (п. 1–3).
2. Настройки: по умолчанию создаётся **закрытая фаза** — всё слушает только `127.0.0.1` (п. 4–5).
3. Владелец создаёт первого администратора, пока снаружи ничего не видно (п. 6).
4. Переключение на домен и Let's Encrypt (п. 7).
5. Стоп-условия (п. 8) и проверка (п. 9). Только после этого — приглашения участникам.

## 0. Что в комплекте

| Файл                              | Зачем                                                                                                                                                                   |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ppm-build.sh`                    | собирает образы из **одного коммита** (`git archive`, не из рабочей папки); пишет ревизию на страницу «О PPM → открытый код»; манифест сборки с `pip freeze`            |
| `ppm-env.sh`                      | создаёт `ppm.env` со сгенерированными секретами и файл парольной фразы бэкапов (оба — права 600), проверяет их, не показывая значения                                   |
| `docker-compose.yml`              | сервисы: PostgreSQL, Valkey (Redis), RabbitMQ, MinIO, миграции, API (HTTP + WebSocket), фоновые задачи, live, web, admin, space, прокси Caddy; инструменты `mc`/`smoke` |
| `docker-compose.internal-tls.yml` | добавляется сам при `PPM_TLS=internal`: закрытая фаза первого запуска, учения восстановления, репетиции                                                                 |
| `proxy/Caddyfile`                 | HTTPS, маршруты (в т.ч. `/ws/` для совместной работы на Холсте), заголовки безопасности, маскирование секретов в логах                                                  |
| `minio/Dockerfile`                | образ хранилища (официальные бинарники MinIO с проверкой SHA-256) и образ `tools` для бэкапов (`mc` + GnuPG)                                                            |
| `ppm-deploy.sh`                   | запуск, проверки, первый администратор, переключение релиза (обновление/откат), логи без секретов, скан логов                                                           |
| `ppm-backup.sh`, `ppm-restore.sh` | зашифрованная резервная копия и восстановление                                                                                                                          |
| `ppm-lib.sh`                      | общие функции скриптов                                                                                                                                                  |
| `smoke/claim_admin.py`            | создание первого администратора инстанса из терминала (п. 6)                                                                                                            |
| `smoke/ppm_smoke.py`              | автоматическая проверка **тестового** стенда (создаёт тестовые учётки — не для боевого сервера)                                                                         |
| `tests/cli-checks.sh`             | проверка отказов скриптов (ничего не запускает)                                                                                                                         |

Принципы:

- Секреты — только в `.runtime/ppm.env`, парольная фраза бэкапов — в `.runtime/ppm.backup-passphrase`. В Git их нет.
  **Копии обоих файлов — в менеджере паролей, отдельно от бэкапов.**
- Данные — в томах Docker (`pgdata`, `minio_data`).
- Наружу открыт только прокси (80/443), и то после п. 7. Базы и MinIO доступны только внутри Docker.
- `--env-file` можно писать в любом месте команды. Скрипт всегда печатает, какой файл взят. Неизвестный
  параметр — ошибка, а не молчаливое игнорирование.

## 1. Подготовка сервера

1. Linux x86_64 (или arm64): ≥ 4 vCPU, 8 ГБ RAM (лучше 16), ≥ 80 ГБ диска; время синхронизировано (NTP).
2. Docker Engine ≥ 24 с плагином Compose v2 (официальный репозиторий Docker), `git`, `openssl`.
3. Оператор — обычный пользователь в группе `docker` (root не нужен). Каталоги:
   ```bash
   sudo mkdir -p /opt/ppm /srv/ppm-backups && sudo chown "$USER": /opt/ppm /srv/ppm-backups && chmod 700 /srv/ppm-backups
   ```
   Контейнеры-инструменты (`mc`, GnuPG, смоук) запускаются с uid/gid оператора, поэтому файлы бэкапов на хосте
   принадлежат ему, а не root.
4. Межсетевой экран: входящие 22 (SSH); 80 и 443 (TCP) — к моменту п. 7. **Порты, опубликованные Docker, обходят
   `ufw`**, поэтому закрытость первой фазы обеспечивает привязка к `127.0.0.1` (п. 4), а не `ufw`.
5. DNS: A-запись (и AAAA, если есть IPv6) выбранного домена → IP сервера. Лучше отдельный поддомен, например
   `ppm.example.ru`: HSTS включается для всего имени. Проверка: `dig +short ppm.example.ru` → IP сервера.
6. Если Docker Hub недоступен (бывает из России), используйте зеркало: при сборке
   `PPM_DOCKERHUB_MIRROR=mirror.gcr.io`. Образы закреплены по digest, поэтому содержимое то же.

## 2. Исходники

```bash
git clone --recurse-submodules <адрес репозитория PPM> /opt/ppm && cd /opt/ppm
git -C plane-fork checkout <коммит релиза>       # точная ревизия из заметок о выпуске
cd plane-fork/deployments/ppm
```

Если репозиторий ещё не опубликован, перенесите его на сервер архивом `git bundle` или `rsync`. Публикация
исходников — стоп-условие п. 8.

## 3. Сборка образов (на самом сервере — под его архитектуру)

```bash
PPM_DOCKERHUB_MIRROR=docker.io ./ppm-build.sh --rev <коммит релиза> --release rc.1
```

- Займёт ~35–45 мин с нуля. На репетиции (Mac arm64): api 13 мин, web 6, space 6,5, live 5, admin 3, minio 3.
  Скачиваются пакеты npm/PyPI, Alpine и бинарники MinIO с GitHub; повторные попытки встроены, повторный запуск
  продолжает с кэша.
- Образы одного релиза занимают ~4,4 ГБ диска (live и space ~1,5 ГБ каждый — как в upstream Plane).
- На работающем сервере собирайте новый релиз в тихое время: сборка занимает все CPU и заметно
  замедляет ответы (на репетиции отдельные запросы под нагрузкой сборки шли до 10–20 с).
- Результат — образы `ppm/<сервис>:rc.1` (в т.ч. `ppm/tools:rc.1` для бэкапов) и в `.runtime/builds/`:
  `rc.1.json` (ревизия, digest базовых образов, id образов, все флаги web) и `rc.1.pip-freeze.txt` (точные версии
  Python-зависимостей, включая транзитивные; SHA-256 — в манифесте).
- Флаги облика задаются при сборке. `PPM_DESIGN_V2=1` — новый облик (по умолчанию). Откат облика —
  пересобрать web с `PPM_DESIGN_V2=0` (п. 12).

## 4. Настройки и секреты

```bash
./ppm-env.sh init --domain ppm.example.ru --release rc.1 --output .runtime/ppm.env
```

- Создаются `.runtime/ppm.env` и `.runtime/ppm.backup-passphrase` (права 600). Секреты и фраза генерируются
  автоматически и **не выводятся**.
- По умолчанию — **закрытая фаза**: `PPM_TLS=internal` (сертификат локального CA Caddy) и
  `PPM_BIND_ADDRESS=127.0.0.1` (порты слушают только на самом сервере). Свободная регистрация выключена:
  `PPM_ENABLE_SIGNUP=0`.
- **Сразу** сохраните оба файла в менеджер паролей:
  - без `SECRET_KEY` восстановленная база не прочитает зашифрованные настройки инстанса (например, пароль SMTP);
  - без парольной фразы **ни одна копия не восстановится**.
- Проверка в любой момент: `./ppm-env.sh check .runtime/ppm.env`. Необязательные параметры (размер загрузок, число
  воркеров, GitHub App) — в `ppm.env.example`. Секреты через `ppm-env.sh set` не меняются (п. 13).

## 5. Первый запуск (закрыто)

```bash
./ppm-deploy.sh --env-file .runtime/ppm.env up
```

`up` делает четыре вещи:

1. поднимает сервисы;
2. применяет миграции (сервис `migrator`);
3. ждёт, пока все станут `healthy` (у фоновых `worker` и `beat-worker` тоже есть проверки);
4. запускает **preflight**: база, Redis, очередь, хранилище (+ запись/чтение), realtime.

Успех выглядит так:

```
{"checks": {"broker": "ok", "database": "ok", "object_storage": "ok", "object_storage_io": "ok", "realtime": "ok", "redis": "ok"}, "status": "ok"}
ppm-deploy: ppm is up at https://ppm.example.ru (release rc.1, PRIVATE: ports on 127.0.0.1 only).
```

Если какой-то пункт `fail` — см. п. 15. Состояние: `./ppm-deploy.sh --env-file .runtime/ppm.env status`, логи без
секретов: `... logs api`. На репетиции первый запуск (миграции пустой БД) занял ~2–3 мин, `restart` — ~1,5 мин.

## 6. Первый администратор — делает владелец, до открытия доступа

Пока порты закрыты, никто посторонний не может «занять» первого администратора. Владелец в SSH-сеансе на
сервере (или оператор, передав ему клавиатуру) выполняет:

```bash
./ppm-deploy.sh --env-file .runtime/ppm.env claim-admin --email <e-mail владельца>
```

- Скрипт спросит имя и дважды пароль (не отображается; ≥ 12 символов). Пароль нигде не сохраняется и не
  печатается. Телеметрия Plane выключается.
- Если администратор уже есть — отказ «Администратор инстанса уже создан».

Затем оператор делает этот аккаунт глобальным администратором PPM (только он создаёт проекты):

```bash
./ppm-deploy.sh --env-file .runtime/ppm.env manage ppm_global_admin grant \
  --email <e-mail владельца> --reason "Первый глобальный администратор PPM" --bootstrap
```

Следующих администраторов назначает уже действующий:
`... grant --email <e-mail> --actor-email <свой e-mail> --reason "..."`. Список: `... manage ppm_global_admin list`.

## 7. Открытие по домену (Let's Encrypt)

Заранее: DNS указывает на сервер (`dig +short <домен>`), в облаке и `ufw` открыты 80 и 443.

```bash
./ppm-env.sh set .runtime/ppm.env PPM_TLS admin@example.ru      # e-mail для уведомлений Let's Encrypt
./ppm-env.sh set .runtime/ppm.env PPM_BIND_ADDRESS 0.0.0.0
./ppm-env.sh check .runtime/ppm.env
./ppm-deploy.sh --env-file .runtime/ppm.env up
```

- Caddy получает сертификат **при старте**. preflight проверяет хранилище через публичный адрес, поэтому без
  сертификата будет `object_storage` fail: проверьте DNS/порты (`logs proxy`) и повторите
  `./ppm-deploy.sh --env-file .runtime/ppm.env preflight`.
- Тестовый (staging) CA Let's Encrypt **не используйте**: сервер ему не доверяет, preflight хранилища не пройдёт.
  Лимиты боевого Let's Encrypt однократному выпуску не мешают — главное, проверить DNS и порты до переключения.
- `ppm-env.sh check` не даст включить Let's Encrypt при закрытых портах и не даст открыть порты с локальным CA.
- HSTS на один год включён по умолчанию (`PPM_HSTS_MAX_AGE`). После выпуска домен работает только по HTTPS.
- Проверка: `curl -sI https://ppm.example.ru | head -1` → `HTTP/2 200`; владелец входит на `https://<домен>/`.

## 8. Перед тем как открыть доступ людям

Стоп-условия. Пока хоть один пункт не выполнен, **не приглашайте участников и не публикуйте адрес**.

1. **Исходный код (AGPL-3.0, §13) — решение и действие владельца.** Точная ревизия сборки опубликована в
   репозитории форка, и ссылка «Исходный код» на странице «О PPM → открытый код» (`https://<домен>/about/open-source`)
   открывается и ведёт на `https://github.com/Imil1914/plane/tree/<ревизия>`. Ревизия на странице совпадает с
   `source_revision` в `.runtime/builds/<релиз>.json`.
2. **Лицензия tldraw — решение владельца.** Условия лицензии tldraw SDK (3.15.6, см. `/opt/ppm/THIRD_PARTY_NOTICES.md` — в корне репозитория PPM, не в комплекте)
   приняты владельцем; водяной знак tldraw на Холсте остаётся и не скрывается. Решение записано в заметках о выпуске.
3. **Администратор и регистрация.** Администратор инстанса — владелец (п. 6); в god-mode → Authentication свободная
   регистрация **выключена** (включать — только осознанным решением владельца); участники входят по приглашениям.
4. **Бэкапы.** Ежедневная зашифрованная копия настроена (п. 10), первая копия вынесена за пределы сервера,
   парольная фраза лежит в менеджере паролей отдельно от копий; учения восстановления (п. 11) пройдены хотя бы раз.
5. **Проверки после выкатки** (п. 9) зелёные, `scan-logs` — «clean».

## 9. Проверка после выкатки (боевой сервер — без тестовых данных)

1. `./ppm-deploy.sh --env-file .runtime/ppm.env preflight` — всё `ok`; `status` — все `healthy`.
2. Вручную, 10 минут:
   - войти;
   - создать Work Item с вложением;
   - открыть Холст, добавить фигуры, обновить страницу — фигуры на месте;
   - на второй вкладке или у второго участника видно присутствие и правки без перезагрузки: это WebSocket.
3. Хранилище: загрузить файл, открыть предпросмотр, скачать; загрузить новую версию и открыть старую.
4. Поиск по проекту находит созданный Work Item (через минуту — индексация идёт в фоне).
5. «О PPM → открытый код» показывает точную ревизию и релиз; ссылка на исходники открывается.
6. `./ppm-deploy.sh --env-file .runtime/ppm.env scan-logs` — «clean»: в логах нет паролей, ключей API, токенов,
   подписанных ссылок, cookie сессий и значений из `ppm.env`. Сам сканер проверяется так: `scan-logs --self-test`
   (подкладывает пример каждого вида секрета — каждый должен быть найден). Любая находка — инцидент: выяснить
   источник по `logs <сервис>` и сменить затронутый секрет (п. 13). Журналы сервисов пишут только метод, путь
   **без строки запроса** (ссылки сброса пароля и приглашений, коды OAuth в них не попадают), статус и время; сегменты
   пути, которые сами являются токеном (`/auth/reset-password/<uid>/<token>/`), маскируются.

Автоматическая проверка (`./ppm-deploy.sh smoke bootstrap|verify`) — **только на тестовом стенде**. Она создаёт
тестового администратора и пользователя и делает его глобальным администратором.

## 10. Резервное копирование (зашифрованное)

```bash
./ppm-backup.sh --env-file .runtime/ppm.env --output-dir /srv/ppm-backups
```

- **Результат** — три файла в `/srv/ppm-backups` (каталог 700, файлы 600):
  - `ppm-<UTC>.tar.gz.gpg` — зашифрованный архив (GnuPG, AES-256, парольная фраза из
    `.runtime/ppm.backup-passphrase`);
  - `ppm-<UTC>.manifest.json` — открытая опись без секретов: релиз, ревизия, число таблиц, строк и файлов;
  - `ppm-<UTC>.tar.gz.gpg.sha256` — контрольная сумма архива (для копий за пределами сервера).
- **В архиве:**
  - полный дамп PostgreSQL: Work Items, все доски со **всеми версиями**, метаданные и версии Хранилища, индекс
    поиска, пользователи;
  - все объекты хранилища: вложения Plane и файлы Хранилища (`ppm-vault/…`);
  - число строк каждой таблицы дампа, опись, `SHA256SUMS`.
- Открытые данные существуют только во временном каталоге 700 в `.runtime/ppm/` (не в `/srv/ppm-backups`) во время
  работы скрипта; он удаляется сразу после шифрования, при ошибке — сам, а остатки прерванного прогона (питание,
  `kill -9`) — при следующем запуске. Перед тем как считать копию готовой, скрипт пробно расшифровывает её той же
  фразой.
- **Не в копии:** `ppm.env` и парольная фраза (храните в менеджере паролей, **не рядом с копиями**), кэш Redis и
  очереди RabbitMQ (восстанавливаются сами), сертификаты (выпускаются заново).
- **Ротация:** остаются 7 последних копий (`PPM_BACKUP_KEEP` в `ppm.env` или `--keep N`), считая только что
  сделанную, и только копии **этого** проекта (`ppm-<UTC>.tar.gz.gpg`; копии учений `ppm-drill-…` не учитываются и
  не удаляются).
- Сервис при бэкапе не останавливается. Дамп консистентен (одна транзакция), объекты копируются сразу после него.
  Файл, загруженный в эти секунды, может попасть в копию без записи в базе — это безопасно. Файл, удалённый в эти
  секунды, может не попасть в копию, хотя запись о нём в базе осталась, — такой файл после восстановления не
  откроется. Окно — секунды; ради точной копии делайте бэкап в тихое время.
- Регулярно: cron раз в сутки + копирование за пределы сервера **только трёх файлов каждой копии**
  (`*.tar.gz.gpg`, `*.manifest.json`, `*.tar.gz.gpg.sha256`; место и срок хранения — решение владельца):
  ```cron
  30 3 * * * cd /opt/ppm/plane-fork/deployments/ppm && ./ppm-backup.sh --env-file .runtime/ppm.env --output-dir /srv/ppm-backups >>/srv/ppm-backups/backup.log 2>&1
  ```
  После первого ночного прогона проверьте: `ls -l /srv/ppm-backups` — владелец файлов — оператор, права `-rw-------`.
- Копия считается существующей только после проверки восстановлением (п. 11), хотя бы раз в месяц и перед
  каждым обновлением.
- На репетиции копия небольшой базы (148 таблиц, несколько файлов) делалась за 4–5 с.

## 11. Восстановление

Всегда в **новый** проект. До любого запуска скрипт проверяет, что у целевого проекта нет ни контейнеров, ни томов
(иначе отказ — ничего не запускается и не пересоздаётся, работающий проект не трогается), а после запуска баз —
что база и хранилище пустые.

### Учения (раз в месяц и перед обновлением) — на этом же сервере, ничего не открывая наружу

```bash
./ppm-env.sh init --domain ppm-drill.localhost --release <релиз из .manifest.json> \
  --https-port 9443 --http-port 9080 --output .runtime/drill.env      # проект: ppm-drill
./ppm-restore.sh --env-file .runtime/drill.env --backup /srv/ppm-backups/ppm-<UTC>.tar.gz.gpg \
  --passphrase-file <файл фразы, сохранённый из менеджера паролей> --drill
```

- Для домена `*.localhost` проект по умолчанию — `ppm-drill`; имя боевого проекта `ppm` для него запрещено
  (`ppm-env.sh check`), поэтому учения не могут попасть в контейнеры и тома боевого стека.
- Домен `*.localhost`, локальный CA и порты только на `127.0.0.1` — копия с реальными данными не видна снаружи.
  Фраза берётся **из менеджера паролей** — так учения заодно проверяют, что сохранённая копия фразы верна.
- `--drill` запускает приложение **без** `worker` и `beat-worker`: копия не отправляет писем, уведомлений и вебхуков.
  Это запоминается для проекта: `restart`, `up` и `release` копии тоже не запускают их.
  У копии свой `SECRET_KEY`, поэтому и сохранённый в базе пароль SMTP ей не прочитать.
- Посмотреть копию: на своём компьютере `ssh -L 9443:127.0.0.1:9443 <сервер>`, затем в браузере
  `https://ppm-drill.localhost:9443` (браузер предупредит о локальном сертификате — для учений это нормально).
  Войти своим аккаунтом и проверить: доска и её старая версия, файл Хранилища и его старая версия, Work Item с
  вложением, поиск.
- После учений:
  ```bash
  ./ppm-deploy.sh --env-file .runtime/drill.env destroy --confirm-project ppm-drill
  rm .runtime/drill.env .runtime/drill.backup-passphrase
  ```
  `destroy` удаляет стек, только если: `--env-file` указан явно; домен в нём — `*.localhost`; проект — не боевой
  `ppm`; работающие контейнеры этого проекта обслуживают тот же `*.localhost`-домен (а не чужой); имя проекта
  набрано ещё раз. Во всех остальных случаях — отказ до любого вызова `docker compose down`.

### Авария (новый сервер, тот же домен)

1. Подготовьте сервер и исходники (п. 1–2), соберите **тот же релиз**, что в `.manifest.json` копии (п. 3).
2. Из менеджера паролей положите `ppm.env` и `ppm.backup-passphrase` в `.runtime/` (`chmod 600` обоим). Старый
   `ppm.env` сохраняет `SECRET_KEY` — настройки инстанса (SMTP и т. п.) останутся читаемыми.
3. Переключите DNS на новый сервер, откройте 80/443 (сертификат выпускается при старте).
4. Восстановите:
   ```bash
   ./ppm-restore.sh --env-file .runtime/ppm.env --backup <копия>.tar.gz.gpg
   ```
5. Проверка п. 9.

Если восстановление на новом сервере оборвалось посередине, повтор откажет («project ppm already exists»): остались
контейнеры и тома неудачной попытки. Только на **новом** сервере без живых данных удалите их
(`./ppm-deploy.sh --env-file .runtime/ppm.env compose down -v`) и повторите шаг 4.

### Что делает `ppm-restore.sh`

1. сверяет SHA-256 архива (если рядом лежит `.sha256`);
2. расшифровывает во временный каталог 700 (удаляется в конце) и проверяет `SHA256SUMS`; при неверной фразе —
   «cannot decrypt … nothing was restored»;
3. сверяет релиз цели с релизом копии (иначе отказ; `--allow-release-mismatch` — только осознанно, если старых
   образов нет: более новый релиз затем применит миграции вперёд);
4. поднимает только базы и хранилище (проект до этого не существовал — проверено до всех действий) и проверяет,
   что они пустые;
5. восстанавливает дамп и сверяет **число строк каждой таблицы** с дампом;
6. возвращает все объекты и сверяет их число;
7. запускает приложение и preflight.

На репетиции восстановление небольшой базы заняло ~1–2 мин; время растёт с объёмом базы и файлов.

## 12. Обновление и откат

**Обновление:**

1. Исходники новой версии:
   ```bash
   cd /opt/ppm && git fetch --recurse-submodules && git -C plane-fork fetch
   git -C plane-fork checkout <новый коммит> && cd plane-fork/deployments/ppm
   ```
2. `./ppm-build.sh --rev <новый коммит> --release rc.2`
3. `./ppm-backup.sh --env-file .runtime/ppm.env --output-dir /srv/ppm-backups` (п. 10).
4. `./ppm-deploy.sh --env-file .runtime/ppm.env release rc.2` — новые миграции применяются автоматически, затем
   preflight. Журнал переключений — `.runtime/ppm/releases.log`.
5. Проверка п. 9.

**Откат приложения:** `./ppm-deploy.sh --env-file .runtime/ppm.env release rc.1`.

- Для отката нужны образы прошлого релиза: **не удаляйте их** (`docker image prune -a` удалит). Старые релизы
  удаляйте поимённо (`docker image rm ppm/<сервис>:<релиз>`), когда новый проверен.
- Схема базы остаётся новой, миграции назад **не** выполняются. Так можно, только если миграции релиза
  совместимы со старым кодом (добавляют таблицы и столбцы с NULL или значениями по умолчанию). Это проверяется
  репетицией отката и указывается в заметках о выпуске.
- Если нет — восстановление из копии, сделанной перед обновлением (п. 11, «Авария», в пустой проект).
- Для rc.1 откат отрепетирован (предыдущая версия ↔ rc.1, миграции `ppm_canvas` 0009–0010 и `ppm_git` 0006–0007):
  старый код читает и пишет данные, записанные новым. Предложения записи в Git старого одношагового формата при
  обновлении закрываются с пояснением и не применяются; предложение, созданное старой версией во время отката,
  после возврата на rc.1 тоже не применится — нужно подготовить новый предпросмотр.

**Откат облика (v2 → v1):** облик задаётся при сборке web. Соберите тот же коммит с другим тегом — пересоберётся
только web, остальные образы возьмутся из кэша — и переключитесь на него:

```bash
PPM_DESIGN_V2=0 ./ppm-build.sh --rev <тот же коммит> --release rc.1-v1
./ppm-deploy.sh --env-file .runtime/ppm.env release rc.1-v1
```

Данные и схема не меняются. Возврат — `... release rc.1`.

Запись в Git по умолчанию выключена: `PPM_GIT_WRITE_ENABLED=0`. Включать только после живой проверки.

## 13. Ротация секретов (кратко)

Перед ротацией — `./ppm-backup.sh`. Значения генерируйте так: `openssl rand -hex 32`. После — новая копия
`ppm.env` в менеджер паролей.

| Секрет                                     | Как сменить                                                                                                                                                                                                                    | Последствия                                                                                                        |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `SECRET_KEY`                               | новое значение в `ppm.env` → `./ppm-deploy.sh up`                                                                                                                                                                              | все выйдут из системы; зашифрованные настройки инстанса (SMTP и т. п.) ввести заново в god-mode                    |
| `LIVE_SERVER_SECRET_KEY`                   | новое значение → `up`                                                                                                                                                                                                          | нет                                                                                                                |
| `POSTGRES_PASSWORD`                        | `./ppm-deploy.sh compose exec plane-db psql -U plane -d plane`, в psql `\password plane` (ввод без отображения) → новое значение в `ppm.env` → `up`                                                                            | короткий перезапуск                                                                                                |
| `RABBITMQ_PASSWORD`                        | `./ppm-deploy.sh compose exec plane-mq rabbitmqctl change_password plane <новый>` (затем очистите историю shell) → `ppm.env` → `up`                                                                                            | короткий перезапуск                                                                                                |
| `MINIO_ACCESS_KEY/SECRET_KEY` (root MinIO) | ⚠ **не отрепетировано** — только по процедуре ниже                                                                                                                                                                             | подписанные ссылки, выданные до смены, перестанут работать; при ошибке MinIO не стартует — возврат старых значений |

Секреты никогда не вставляйте в задачи и чаты; `logs` и `scan-logs` показывают ключи, но не значения.

### Смена root-учётки MinIO — процедура (⚠ в RC не отрепетирована)

> **Предупреждение.** Эта процедура в release candidate **не проверялась ни разу**. Root-учётка MinIO — единственная
> учётка хранилища: её используют API, фоновые задачи, `minio-init` и бэкапы. Ошибка = нет доступа ко всем файлам
> (вложения и Хранилище) до возврата старых значений. Выполнять только в окно обслуживания, только после свежего
> бэкапа и **сначала на учебной копии** (п. 11). Если что-то пошло не так — сразу шаг 7 (откат).

1. Свежая копия: `./ppm-backup.sh --env-file .runtime/ppm.env --output-dir /srv/ppm-backups`; убедитесь, что копия
   `ppm.env` со **старыми** значениями есть в менеджере паролей.
2. Репетиция на учебной копии: восстановите эту копию в проект `ppm-drill` (п. 11, «Учения»), выполните на нём шаги
   3–6 (в файле `.runtime/drill.env`) и проверьте скачивание файла через SSH-туннель. Только если всё прошло —
   продолжайте на боевом сервере; учебную копию затем удалите (`destroy`).
3. Новые значения (не показываются на экране, сразу в файл-черновик 600):
   ```bash
   umask 077; { echo "MINIO_ACCESS_KEY=ppm$(openssl rand -hex 10)"; echo "MINIO_SECRET_KEY=$(openssl rand -hex 32)"; } > .runtime/minio-new.txt
   ```
4. Замените две строки `MINIO_ACCESS_KEY=` и `MINIO_SECRET_KEY=` в `.runtime/ppm.env` строками из
   `.runtime/minio-new.txt` в текстовом редакторе (`ppm-env.sh set` секреты намеренно не меняет), удалите черновик
   (`rm .runtime/minio-new.txt`), проверьте: `./ppm-env.sh check .runtime/ppm.env` (права 600, формат).
5. `./ppm-deploy.sh --env-file .runtime/ppm.env up` — пересоздаёт `plane-minio` (новая root-учётка, те же данные в томе
   `minio_data`), `minio-init`, `api`, `worker`, `beat-worker`; в конце preflight `object_storage_io` должен быть `ok`
   (запись и чтение новой учёткой).
6. Проверка: скачать вложение Work Item и файл Хранилища, открыть предпросмотр; сделать бэкап
   (`ppm-backup.sh` — он ходит в MinIO новой учёткой). Сохраните новый `ppm.env` в менеджер паролей.
7. **Откат**, если `plane-minio` не становится `healthy`, preflight хранилища — `fail` или файлы не открываются:
   верните старые строки из менеджера паролей в `.runtime/ppm.env` и выполните `./ppm-deploy.sh --env-file
.runtime/ppm.env up`. Данные в томе при смене учётки не меняются; если и откат не помог — восстановление из
   копии шага 1 в новый проект (п. 11, «Авария»).

## 16. Известные ограничения комплекта RC

- **Content-Security-Policy не задан** (решение — после RC). Холст (tldraw) использует встроенные стили, `blob:`-воркеры
  и `data:`-изображения, предпросмотр PDF — iframe; политику, которая ничего из этого не ломает, нужно отдельно
  подобрать и прогнать по Холсту, Хранилищу и god-mode. Сейчас действуют: `nosniff`, `X-Frame-Options SAMEORIGIN`,
  `Referrer-Policy`, `Permissions-Policy`, HSTS; скачивания Хранилища отдаются с `Content-Security-Policy:
default-src 'none'; sandbox`; бакет закрытый, подписанные ссылки живут 5 минут.
- Журналы запросов без строки запроса и без заголовков: прокси (Caddy — маскирует параметры и удаляет cookie,
  ключи API, `Referer`, `Location`), `api` (путь без query, токен сброса пароля в пути маскируется), `web`/`admin`
  (nginx: путь без query, без `Referer`; ошибки уровня запроса не пишутся), `space` и `live` (путь без query, без
  заголовков). `worker` работает с уровнем WARNING: аргументы задач (в них токены писем) не пишутся. В журнале
  внешнего API в базе (`api_activity_logs`, только запросы с ключом API) значения параметров-учётных данных и
  заголовки `Cookie`/`Authorization`/`Referer` заменяются на `[redacted]`; тела запросов там хранятся — это журнал
  аудита upstream Plane. Флаг `--access-logfile -` в команде запуска API (upstream) фактически ничего не пишет:
  конфигурация логов Django отключает журнал uvicorn (проверено на стенде).
- `max_header_size 25MB` в Caddy унаследован от upstream Plane; тело запроса ограничено 16 МБ (прокси) и лимитом
  загрузок приложения.
- Отказ MinIO: загрузка в Хранилище ждёт ~10 с (всего 2 попытки клиента S3; настраивается `PPM_S3_*` в
  `ppm.env`). Задачи экспорта и команды создания бакета используют свои клиенты S3 без этих ограничений.
- Серверное чтение файла Хранилища в память ограничено: предпросмотр — 16 МБ, остальное — 250 МБ на файл.
- DRF 3.17.1 оставлен. Совет CVE-2026-73228 нейтрализован: upstream-middleware ограничивает тело запроса
  (413), прокси — 16 МБ. Совет CVE-2026-73229 касается `AdminRenderer`, PPM его не использует.
  Предупреждения `pnpm audit` у зависимостей upstream Plane — в отчёте RC-A.
- Мониторинга и алертов нет: проверки вручную по п. 14.
- Образы собираются на сервере, реестра образов нет. `apk upgrade` при сборке — сборки воспроизводимы по
  исходникам, базовым образам и `pip freeze`, но не побитово.
- Формат копий — `ppm-backup/2` (зашифрованный). Незашифрованные каталоги ранних репетиций RC этим скриптом не
  восстанавливаются.
- Смена root-учётки MinIO описана, но не отрепетирована (п. 13, процедура с предупреждением).
- Страница god-mode (upstream Plane) содержит ссылки на plane.so — используется только администратором.
