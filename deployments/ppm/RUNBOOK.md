# PPM — развёртывание и эксплуатация (release candidate)

Инструкция для сервера с одним доменом по HTTPS и Git-сервером команд на `git.<домен>` (п. 17). Всё, кроме первого
администратора и решений из п. 8, делает оператор. Шаги **владельца** помечены. Команды выполняются из каталога
`/opt/ppm/plane-fork/deployments/ppm/`.

> Все шаги отрепетированы локально (Caddy с локальным CA вместо Let's Encrypt, домены `*.localhost`).
> Протокол и измеренные времена — `.superpowers/sdd/2026-09-26-ppm-rc/task-RCA-report.md`.

Порядок первого развёртывания: **закрыто → администратор → открыто → стоп-условия → люди**.

1. Сервер, исходники, сборка (п. 1–3).
2. Настройки: по умолчанию создаётся **закрытая фаза** — всё слушает только `127.0.0.1` (п. 4–5).
3. Владелец создаёт первого администратора, пока снаружи ничего не видно (п. 6).
4. Переключение на домен и Let's Encrypt (п. 7).
5. Стоп-условия (п. 8) и проверка (п. 9). Только после этого — приглашения участникам.

## 0. Что в комплекте

| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `ppm-env.sh`                      | создаёт `ppm.env` со сгенерированными секретами и файл парольной фразы бэкапов (оба — права 600), проверяет их, не показывая значения; `add-git` дописывает ключи Git-сервера в файл RC.1, не меняя остальных строк     |
| `docker-compose.yml`              | сервисы: PostgreSQL, Valkey (Redis), RabbitMQ, MinIO, миграции, API (HTTP + WebSocket), фоновые задачи, live, web, admin, space, прокси Caddy; инструменты `mc`/`smoke`                                                 |
| `docker-compose.internal-tls.yml` | добавляется сам при `PPM_TLS=internal`: закрытая фаза первого запуска, учения восстановления, репетиции                                                                                                                 |
| `docker-compose.git.yml`          | добавляется сам при `PPM_GIT_SERVER_ENABLED=1`: Git-сервер Forgejo 15 LTS (`forgejo`), его база и роль в том же PostgreSQL (`forgejo-db-init`), инструменты бэкапа; переменные `PPM_FORGEJO_*` для API (п. 17)          |
| `docker-compose.git-ssh.yml`      | добавляется сам при `PPM_GIT_SSH_ENABLED=1`: git по SSH на порту `2222` (п. 17.1, 17.11)                                                                                                                                |
| `proxy/Caddyfile`                 | HTTPS, маршруты (в т.ч. `/ws/` для совместной работы на Холсте), заголовки безопасности, маскирование секретов в логах; сайт Git-сервера `git.<домен>` — `proxy/git-server-1.caddy` (только при включённом Git-сервере) |
| `minio/Dockerfile`                | образ хранилища (официальные бинарники MinIO с проверкой SHA-256) и образ `tools` для бэкапов (`mc` + GnuPG)                                                                                                            |
| `forgejo/`                        | `db-init.sql` — база и роль Forgejo (идемпотентно, пароль из окружения); `git_bootstrap.py` — токен PPM и системный вебхук (`git-bootstrap`)                                                                            |
| `ppm-deploy.sh`                   | запуск, проверки, первый администратор, переключение релиза (обновление/откат), логи без секретов, скан логов; Git-сервер: первичная настройка (`git-bootstrap`) и администратор Forgejo (`git-admin`)                  |
| `ppm-backup.sh`, `ppm-restore.sh` | зашифрованная резервная копия и восстановление — вместе с Git-сервером (база и данные Forgejo)                                                                                                                          |
| `ppm-lib.sh`                      | общие функции скриптов                                                                                                                                                                                                  |
| `smoke/claim_admin.py`            | создание первого администратора инстанса из терминала (п. 6)                                                                                                                                                            |
| `smoke/ppm_smoke.py`              | автоматическая проверка **тестового** стенда (создаёт тестовые учётки — не для боевого сервера)                                                                                                                         |
| `tests/cli-checks.sh`             | проверка отказов скриптов (ничего не запускает); `tests/git_bootstrap_test.py` — первичная настройка Git-сервера на поддельном Forgejo (без сети)                                                                       |

Принципы:

- Секреты — только в `.runtime/ppm.env`, парольная фраза бэкапов — в `.runtime/ppm.backup-passphrase`. В Git их нет.
  **Копии обоих файлов — в менеджере паролей, отдельно от бэкапов.**
- Данные — в томах Docker (`pgdata`, `minio_data`, `forgejo_data` — репозитории Git-сервера).
- Наружу открыты только прокси (80/443) и git по SSH (2222, п. 17.1), и то после п. 7. Базы, MinIO и сам Forgejo
  доступны только внутри Docker.
- `--env-file` можно писать в любом месте команды. Скрипт всегда печатает, какой файл взят. Неизвестный
  параметр — ошибка, а не молчаливое игнорирование.

## 1. Подготовка сервера

1. Linux x86_64 (или arm64): ≥ 4 vCPU, 8 ГБ RAM (лучше 16), ≥ 100 ГБ диска (код команд Git-сервера — на этом же
   диске); время синхронизировано (NTP).
2. Docker Engine ≥ 24 с плагином Compose v2 (официальный репозиторий Docker), `git`, `openssl`.
3. Оператор — обычный пользователь в группе `docker` (root не нужен). Каталоги:
   ```bash
   sudo mkdir -p /opt/ppm /srv/ppm-backups && sudo chown "$USER": /opt/ppm /srv/ppm-backups && chmod 700 /srv/ppm-backups
   ```
   Контейнеры-инструменты (`mc`, GnuPG, смоук) запускаются с uid/gid оператора, поэтому файлы бэкапов на хосте
   принадлежат ему, а не root.
4. Межсетевой экран: входящие 22 (SSH); 80 и 443 (TCP) и 2222 (git по SSH, п. 17.1) — к моменту п. 7. **Порты,
   опубликованные Docker, обходят `ufw`**, поэтому закрытость первой фазы обеспечивает привязка к `127.0.0.1` (п. 4),
   а не `ufw`.
5. DNS: A-запись (и AAAA, если есть IPv6) выбранного домена → IP сервера. Лучше отдельный поддомен, например
   `ppm.example.ru`: HSTS включается для всего имени. Проверка: `dig +short ppm.example.ru` → IP сервера. Вторая
   запись — `git.<домен>` (Git-сервер, п. 17.1) на тот же IP.
6. Если Docker Hub недоступен (бывает из России), используйте зеркало: при сборке
   `PPM_DOCKERHUB_MIRROR=mirror.gcr.io`. Образы закреплены по digest, поэтому содержимое то же.

## 2. Исходники

```bash
git clone --recurse-submodules <адрес репозитория PPM> /opt/ppm && cd /opt/ppm
git -C plane-fork checkout <коммит релиза>       # точная ревизия из заметок о выпуске
cd plane-fork/deployments/ppm
```

Если репозиторий ещё не опубликован, перенесите его на сервер архивом `git bundle` или `rsync`. Публикация
исходников — стоп-условие п. 8.

## 3. Сборка образов (на самом сервере — под его архитектуру)

```bash
PPM_DOCKERHUB_MIRROR=docker.io ./ppm-build.sh --rev <коммит релиза> --release rc.1
```

- Займёт ~35–45 мин с нуля. На репетиции (Mac arm64): api 13 мин, web 6, space 6,5, live 5, admin 3, minio 3.
  Скачиваются пакеты npm/PyPI, Alpine и бинарники MinIO с GitHub; повторные попытки встроены, повторный запуск
  продолжает с кэша.
- Образы одного релиза занимают ~4,4 ГБ диска (live и space ~1,5 ГБ каждый — как в upstream Plane).
- На работающем сервере собирайте новый релиз в тихое время: сборка занимает все CPU и заметно
  замедляет ответы (на репетиции отдельные запросы под нагрузкой сборки шли до 10–20 с).
- Результат — образы `ppm/<сервис>:rc.1` (в т.ч. `ppm/tools:rc.1` для бэкапов) и в `.runtime/builds/`:
  `rc.1.json` (ревизия, digest базовых образов, id образов, все флаги web) и `rc.1.pip-freeze.txt` (точные версии
  Python-зависимостей, включая транзитивные; SHA-256 — в манифесте).
- Флаги облика задаются при сборке. `PPM_DESIGN_V2=1` — новый облик (по умолчанию). Откат облика —
  пересобрать web с `PPM_DESIGN_V2=0` (п. 12).

## 4. Настройки и секреты

```bash
./ppm-env.sh init --domain ppm.example.ru --release rc.1 --output .runtime/ppm.env
```

- Создаются `.runtime/ppm.env` и `.runtime/ppm.backup-passphrase` (права 600). Секреты и фраза генерируются
  автоматически и **не выводятся**.
- По умолчанию — **закрытая фаза**: `PPM_TLS=internal` (сертификат локального CA Caddy) и
  `PPM_BIND_ADDRESS=127.0.0.1` (порты слушают только на самом сервере). Свободная регистрация выключена:
  `PPM_ENABLE_SIGNUP=0`.
- **Сразу** сохраните оба файла в менеджер паролей:
  - без `SECRET_KEY` восстановленная база не прочитает зашифрованные настройки инстанса (например, пароль SMTP);
  - без парольной фразы **ни одна копия не восстановится**.
- Проверка в любой момент: `./ppm-env.sh check .runtime/ppm.env`. Необязательные параметры (размер загрузок, число
  воркеров, GitHub App) — в `ppm.env.example`. Секреты через `ppm-env.sh set` не меняются (п. 13).
- Там же — Git-сервер (п. 17): `git.<домен>`, git по SSH на порту `2222`, образ Forgejo, закреплённый по digest, и его
  секреты `FORGEJO_*`, `PPM_FORGEJO_WEBHOOK_SECRET`. Другое имя или порт — параметры `init`: `--git-domain <имя>`,
  `--git-ssh-port <порт>`. Файл RC.1 без этих ключей: `./ppm-env.sh add-git .runtime/ppm.env` (п. 17.2) — остальные
  строки не меняются.

## 5. Первый запуск (закрыто)

```bash
./ppm-deploy.sh --env-file .runtime/ppm.env up
```

`up` делает четыре вещи:

1. поднимает сервисы;
2. применяет миграции (сервис `migrator`);
3. ждёт, пока все станут `healthy` (у фоновых `worker` и `beat-worker` тоже есть проверки);
4. запускает **preflight**: база, Redis, очередь, хранилище (+ запись/чтение), realtime.

Успех выглядит так:

```
{"checks": {"broker": "ok", "database": "ok", "object_storage": "ok", "object_storage_io": "ok", "realtime": "ok", "redis": "ok"}, "status": "ok"}
ppm-deploy: ppm is up at https://ppm.example.ru (release rc.1, PRIVATE: ports on 127.0.0.1 only).
```

С Git-сервером — ещё строка его проверки (`git_internal`, `git_public`, `git_token`) и напоминание выполнить
`git-bootstrap` (п. 17.3). Если какой-то пункт `fail` — см. п. 15 и 17.13. Состояние:
`./ppm-deploy.sh --env-file .runtime/ppm.env status`, логи без секретов: `... logs api`. На репетиции первый запуск (миграции пустой БД) занял ~2–3 мин, `restart` — ~1,5 мин.

## 6. Первый администратор — делает владелец, до открытия доступа

Пока порты закрыты, никто посторонний не может «занять» первого администратора. Владелец в SSH-сеансе на
сервере (или оператор, передав ему клавиатуру) выполняет:

```bash
./ppm-deploy.sh --env-file .runtime/ppm.env claim-admin --email <e-mail владельца>
```

- Скрипт спросит имя и дважды пароль (не отображается; ≥ 12 символов). Пароль нигде не сохраняется и не
  печатается. Телеметрия Plane выключается.
- Если администратор уже есть — отказ «Администратор инстанса уже создан».

Затем оператор делает этот аккаунт глобальным администратором PPM (только он создаёт проекты):

```bash
./ppm-deploy.sh --env-file .runtime/ppm.env manage ppm_global_admin grant \
  --email <e-mail владельца> --reason "Первый глобальный администратор PPM" --bootstrap
```

Администратора Git-сервера создаёт отдельная команда `git-admin` (п. 17.4) — после `git-bootstrap` (п. 17.3).

Следующих администраторов назначает уже действующий:
`... grant --email <e-mail> --actor-email <свой e-mail> --reason "..."`. Список: `... manage ppm_global_admin list`.

## 7. Открытие по домену (Let's Encrypt)

Заранее: DNS указывает на сервер (`dig +short <домен>` и `dig +short git.<домен>`), в облаке и `ufw` открыты 80, 443
и 2222 (git по SSH).

```bash
./ppm-env.sh set .runtime/ppm.env PPM_TLS admin@example.ru      # e-mail для уведомлений Let's Encrypt
./ppm-env.sh set .runtime/ppm.env PPM_BIND_ADDRESS 0.0.0.0
./ppm-env.sh check .runtime/ppm.env
./ppm-deploy.sh --env-file .runtime/ppm.env up
```

- Caddy получает сертификаты (для домена и `git.<домен>`) **при старте**. preflight проверяет хранилище и
  Git-сервер через публичные адреса, поэтому без сертификата будет `object_storage` или `git_public` fail: проверьте
  DNS/порты (`logs proxy`) и повторите `./ppm-deploy.sh --env-file .runtime/ppm.env preflight`. Порт `2222`
  публикуется на `0.0.0.0` вместе с 80/443.
- Тестовый (staging) CA Let's Encrypt **не используйте**: сервер ему не доверяет, preflight хранилища не пройдёт.
  Лимиты боевого Let's Encrypt однократному выпуску не мешают — главное, проверить DNS и порты до переключения.
- `ppm-env.sh check` не даст включить Let's Encrypt при закрытых портах и не даст открыть порты с локальным CA.
- HSTS на один год включён по умолчанию (`PPM_HSTS_MAX_AGE`). После выпуска домен работает только по HTTPS.
- Проверка: `curl -sI https://ppm.example.ru | head -1` → `HTTP/2 200`; владелец входит на `https://<домен>/`.

## 8. Перед тем как открыть доступ людям

Стоп-условия. Пока хоть один пункт не выполнен, **не приглашайте участников и не публикуйте адрес**.

1. **Исходный код (AGPL-3.0, §13) — решение и действие владельца.** Точная ревизия сборки опубликована в
   репозитории форка, и ссылка «Исходный код» на странице «О PPM → открытый код» (`https://<домен>/about/open-source`)
   открывается и ведёт на `https://github.com/Imil1914/plane/tree/<ревизия>`. Ревизия на странице совпадает с
   `source_revision` в `.runtime/builds/<релиз>.json`.
2. **Лицензия tldraw — решение владельца.** Условия лицензии tldraw SDK (3.15.6, см. `/opt/ppm/THIRD_PARTY_NOTICES.md` — в корне репозитория PPM, не в комплекте)
   приняты владельцем; водяной знак tldraw на Холсте остаётся и не скрывается. Решение записано в заметках о выпуске.
3. **Администратор и регистрация.** Администратор инстанса — владелец (п. 6); в god-mode → Authentication свободная
   регистрация **выключена** (включать — только осознанным решением владельца); участники входят по приглашениям.
4. **Бэкапы.** Ежедневная зашифрованная копия настроена (п. 10), первая копия вынесена за пределы сервера,
   парольная фраза лежит в менеджере паролей отдельно от копий; учения восстановления (п. 11) пройдены хотя бы раз.
5. **Проверки после выкатки** (п. 9) зелёные, `scan-logs` — «clean».

## 9. Проверка после выкатки (боевой сервер — без тестовых данных)

1. `./ppm-deploy.sh --env-file .runtime/ppm.env preflight` — всё `ok`; `status` — все `healthy`.
2. Вручную, 10 минут:
   - войти;
   - создать Work Item с вложением;
   - открыть Холст, добавить фигуры, обновить страницу — фигуры на месте;
   - на второй вкладке или у второго участника видно присутствие и правки без перезагрузки: это WebSocket.
3. Хранилище: загрузить файл, открыть предпросмотр, скачать; загрузить новую версию и открыть старую.
4. Поиск по проекту находит созданный Work Item (через минуту — индексация идёт в фоне).
5. «О PPM → открытый код» показывает точную ревизию и релиз; ссылка на исходники открывается.
6. Git-сервер (п. 17): preflight — `git_internal`, `git_public`, `git_token` — `ok`; администратор Forgejo входит на
   `https://git.<домен>/`; тестовый репозиторий создаётся `git push`, клонируется по HTTPS и по SSH (п. 17.6);
   подключается к проекту в разделе «Код», и коммит с ключом задачи появляется у задачи.
7. `./ppm-deploy.sh --env-file .runtime/ppm.env scan-logs` — «clean»: в логах нет паролей, ключей API, токенов,
   подписанных ссылок, cookie сессий и значений из `ppm.env`. Сам сканер проверяется так: `scan-logs --self-test`
   (подкладывает пример каждого вида секрета — каждый должен быть найден). Проверяются и журналы Git-сервера: сайт
   `git.<домен>` в прокси (git по HTTPS передаёт токен в `Authorization`), Forgejo, ссылки вида
   `https://имя:токен@…`, cookie сессии Forgejo. Любая находка — инцидент: выяснить источник по `logs <сервис>` и
   сменить затронутый секрет (п. 13). Журналы сервисов пишут только метод, путь
   **без строки запроса** (ссылки сброса пароля и приглашений, коды OAuth в них не попадают), статус и время; сегменты
   пути, которые сами являются токеном (`/auth/reset-password/<uid>/<token>/`), маскируются.

Автоматическая проверка (`./ppm-deploy.sh smoke bootstrap|verify`) — **только на тестовом стенде**. Она создаёт
тестового администратора и пользователя и делает его глобальным администратором.

## 10. Резервное копирование (зашифрованное)

```bash
./ppm-backup.sh --env-file .runtime/ppm.env --output-dir /srv/ppm-backups
```

- **Результат** — три файла в `/srv/ppm-backups` (каталог 700, файлы 600):
  - `ppm-<UTC>.tar.gz.gpg` — зашифрованный архив (GnuPG, AES-256, парольная фраза из
    `.runtime/ppm.backup-passphrase`);
  - `ppm-<UTC>.manifest.json` — открытая опись без секретов: релиз, ревизия, число таблиц, строк и файлов;
  - `ppm-<UTC>.tar.gz.gpg.sha256` — контрольная сумма архива (для копий за пределами сервера).
- **В архиве:**
  - полный дамп PostgreSQL: Work Items, все доски со **всеми версиями**, метаданные и версии Хранилища, индекс
    поиска, пользователи;
  - все объекты хранилища: вложения Plane и файлы Хранилища (`ppm-vault/…`);
  - Git-сервер: дамп базы `forgejo` и его данные — репозитории, LFS, вложения, SSH-ключи сервера (п. 17.10);
  - число строк каждой таблицы дампа, опись, `SHA256SUMS`.
- Открытые данные существуют только во временном каталоге 700 в `.runtime/ppm/` (не в `/srv/ppm-backups`) во время
  работы скрипта; он удаляется сразу после шифрования, при ошибке — сам, а остатки прерванного прогона (питание,
  `kill -9`) — при следующем запуске. Перед тем как считать копию готовой, скрипт пробно расшифровывает её той же
  фразой.
- **Не в копии:** `ppm.env` и парольная фраза (храните в менеджере паролей, **не рядом с копиями**), кэш Redis и
  очереди RabbitMQ (восстанавливаются сами), сертификаты (выпускаются заново).
- **Ротация:** остаются 7 последних копий (`PPM_BACKUP_KEEP` в `ppm.env` или `--keep N`), считая только что
  сделанную, и только копии **этого** проекта (`ppm-<UTC>.tar.gz.gpg`; копии учений `ppm-drill-…` не учитываются и
  не удаляются).
- PPM при бэкапе не останавливается; Git-сервер останавливается на время своей копии (секунды, п. 17.10). Дамп
  консистентен (одна транзакция), объекты копируются сразу после него.
  Файл, загруженный в эти секунды, может попасть в копию без записи в базе — это безопасно. Файл, удалённый в эти
  секунды, может не попасть в копию, хотя запись о нём в базе осталась, — такой файл после восстановления не
  откроется. Окно — секунды; ради точной копии делайте бэкап в тихое время.
- Регулярно: cron раз в сутки + копирование за пределы сервера **только трёх файлов каждой копии**
  (`*.tar.gz.gpg`, `*.manifest.json`, `*.tar.gz.gpg.sha256`; место и срок хранения — решение владельца):
  ```cron
  30 3 * * * cd /opt/ppm/plane-fork/deployments/ppm && ./ppm-backup.sh --env-file .runtime/ppm.env --output-dir /srv/ppm-backups >>/srv/ppm-backups/backup.log 2>&1
  ```
  После первого ночного прогона проверьте: `ls -l /srv/ppm-backups` — владелец файлов — оператор, права `-rw-------`.
- Копия считается существующей только после проверки восстановлением (п. 11), хотя бы раз в месяц и перед
  каждым обновлением.
- На репетиции копия небольшой базы (148 таблиц, несколько файлов) делалась за 4–5 с; с Git-сервером (2 репозитория,
  3 МБ) — 20 с, из них Forgejo был остановлен 12 с.

## 11. Восстановление

Всегда в **новый** проект. До любого запуска скрипт проверяет, что у целевого проекта нет ни контейнеров, ни томов
(иначе отказ — ничего не запускается и не пересоздаётся, работающий проект не трогается), а после запуска баз —
что база и хранилище пустые.

### Учения (раз в месяц и перед обновлением) — на этом же сервере, ничего не открывая наружу

```bash
./ppm-env.sh init --domain ppm-drill.localhost --release <релиз из .manifest.json> \
  --https-port 9443 --http-port 9080 --git-ssh-port 9222 --output .runtime/drill.env      # проект: ppm-drill
./ppm-restore.sh --env-file .runtime/drill.env --backup /srv/ppm-backups/ppm-<UTC>.tar.gz.gpg \
  --passphrase-file <файл фразы, сохранённый из менеджера паролей> --drill
```

- Для домена `*.localhost` проект по умолчанию — `ppm-drill`; имя боевого проекта `ppm` для него запрещено
  (`ppm-env.sh check`), поэтому учения не могут попасть в контейнеры и тома боевого стека.
- Домен `*.localhost`, локальный CA и порты только на `127.0.0.1` — копия с реальными данными не видна снаружи.
  Фраза берётся **из менеджера паролей** — так учения заодно проверяют, что сохранённая копия фразы верна.
- `--drill` запускает приложение **без** `worker` и `beat-worker`: копия не отправляет писем, уведомлений и вебхуков.
  Git-сервер копии тоже никуда не обращается (вебхуки и миграции — в закрытый локальный порт, миграции выключены).
  Это запоминается для проекта: `restart`, `up` и `release` копии тоже не запускают их.
- `--git-ssh-port 9222`: порт 2222 уже занят боевым Git-сервером; другие порты копии тоже должны быть свободны.
  У копии свой `SECRET_KEY`, поэтому и сохранённый в базе пароль SMTP ей не прочитать.
- Посмотреть копию: на своём компьютере `ssh -L 9443:127.0.0.1:9443 <сервер>`, затем в браузере
  `https://ppm-drill.localhost:9443` (браузер предупредит о локальном сертификате — для учений это нормально).
  Войти своим аккаунтом и проверить: доска и её старая версия, файл Хранилища и его старая версия, Work Item с
  вложением, поиск. Git-сервер копии — `https://git.ppm-drill.localhost:9443` (туннель тот же): вход
  администратора Forgejo, репозиторий и его история.
- После учений:
  ```bash
  ./ppm-deploy.sh --env-file .runtime/drill.env destroy --confirm-project ppm-drill
  rm .runtime/drill.env .runtime/drill.backup-passphrase
  ```
  `destroy` удаляет стек, только если: `--env-file` указан явно; домен в нём — `*.localhost`; проект — не боевой
  `ppm`; работающие контейнеры этого проекта обслуживают тот же `*.localhost`-домен (а не чужой); имя проекта
  набрано ещё раз. Во всех остальных случаях — отказ до любого вызова `docker compose down`.

### Авария (новый сервер, тот же домен)

1. Подготовьте сервер и исходники (п. 1–2), соберите **тот же релиз**, что в `.manifest.json` копии (п. 3).
2. Из менеджера паролей положите `ppm.env` и `ppm.backup-passphrase` в `.runtime/` (`chmod 600` обоим). Старый
   `ppm.env` сохраняет `SECRET_KEY` — настройки инстанса (SMTP и т. п.) останутся читаемыми.
3. Переключите DNS обоих имён — домена и `git.<домен>` — на новый сервер, откройте 80/443 и 2222 (git по SSH,
   п. 17.1); сертификаты выпускаются при старте.
4. Восстановите:
   ```bash
   ./ppm-restore.sh --env-file .runtime/ppm.env --backup <копия>.tar.gz.gpg
   ```
5. Git-сервер: `./ppm-deploy.sh --env-file .runtime/ppm.env git-bootstrap` — проверит токен PPM (выпустит новый, если
   в сохранённой копии `ppm.env` его нет или он не подходит) и пересоздаст вебхук (п. 17.3).
6. Проверка п. 9.

Если восстановление на новом сервере оборвалось посередине, повтор откажет («project ppm already exists»): остались
контейнеры и тома неудачной попытки. Только на **новом** сервере без живых данных удалите их
(`./ppm-deploy.sh --env-file .runtime/ppm.env compose down -v`) и повторите шаг 4.
Отпечаток SSH-ключа Git-сервера после восстановления тот же (ключи сервера — в копии): разработчикам ничего менять
не нужно.

### Что делает `ppm-restore.sh`

1. сверяет SHA-256 архива (если рядом лежит `.sha256`);
2. расшифровывает во временный каталог 700 (удаляется в конце) и проверяет `SHA256SUMS`; при неверной фразе —
   «cannot decrypt … nothing was restored»;
3. сверяет релиз цели с релизом копии (иначе отказ; `--allow-release-mismatch` — только осознанно, если старых
   образов нет: более новый релиз затем применит миграции вперёд);
4. поднимает только базы и хранилище (проект до этого не существовал — проверено до всех действий) и проверяет,
   что они пустые;
5. восстанавливает дамп и сверяет **число строк каждой таблицы** с дампом;
6. возвращает все объекты и сверяет их число;
7. если в копии есть Git-сервер: база `forgejo` (число строк каждой таблицы), данные, «репозиториев на диске = записей в
   базе = как в копии», `git fsck` пяти случайных репозиториев (п. 17.10); архив с Git-сервером — только в окружение,
   где он включён;
8. запускает приложение и preflight.

На репетиции восстановление небольшой базы заняло ~1–2 мин (с Git-сервером — 69 с); время растёт с объёмом базы,
файлов и кода. Копии RC.1 (`ppm-backup/2`, без Git-сервера) восстанавливаются как раньше; Forgejo цели стартует
пустым.

## 12. Обновление и откат

**Обновление:**

1. Исходники новой версии:
   ```bash
   cd /opt/ppm && git fetch --recurse-submodules && git -C plane-fork fetch
   git -C plane-fork checkout <новый коммит> && cd plane-fork/deployments/ppm
   ```
2. `./ppm-build.sh --rev <новый коммит> --release rc.2`
3. `./ppm-backup.sh --env-file .runtime/ppm.env --output-dir /srv/ppm-backups` (п. 10).
4. Только при переходе с RC.1 (Git-сервер появился в RC.2): `./ppm-env.sh add-git .runtime/ppm.env` — добавит ключи
   Git-сервера, ничего не меняя в остальных (п. 17.2); DNS `git.<домен>` и порт 2222 — п. 17.1.
5. `./ppm-deploy.sh --env-file .runtime/ppm.env release rc.2` — новые миграции применяются автоматически, затем
   preflight. Журнал переключений — `.runtime/ppm/releases.log`.
6. Только при переходе с RC.1: `git-bootstrap` (п. 17.3), `git-admin` для владельца (п. 17.4); новая копия `ppm.env`
   — в менеджер паролей.
7. Проверка п. 9.

**Откат приложения:** `./ppm-deploy.sh --env-file .runtime/ppm.env release rc.1`.

- **С Git-сервером откат на rc.1 отключает его сайт.** Прокси rc.1 не знает `git.<домен>`: веб-интерфейс Forgejo и
  git по HTTPS перестанут открываться до возврата на rc.2. Git по SSH, данные Forgejo и приложение PPM rc.1
  продолжают работать (rc.1 Git-сервер просто не видит). Поэтому `release rc.1` при включённом Git-сервере откажет
  с объяснением; осознанный откат — `release rc.1 --allow-git-site-loss`. Preflight тогда показывает
  `git_public: absent` (это не ошибка). Возврат — `release rc.2`.

- Для отката нужны образы прошлого релиза: **не удаляйте их** (`docker image prune -a` удалит). Старые релизы
  удаляйте поимённо (`docker image rm ppm/<сервис>:<релиз>`), когда новый проверен.
- Схема базы остаётся новой, миграции назад **не** выполняются. Так можно, только если миграции релиза
  совместимы со старым кодом (добавляют таблицы и столбцы с NULL или значениями по умолчанию). Это проверяется
  репетицией отката и указывается в заметках о выпуске.
- Если нет — восстановление из копии, сделанной перед обновлением (п. 11, «Авария», в пустой проект).
- Для rc.1 откат отрепетирован (предыдущая версия ↔ rc.1, миграции `ppm_canvas` 0009–0010 и `ppm_git` 0006–0007):
  старый код читает и пишет данные, записанные новым. Предложения записи в Git старого одношагового формата при
  обновлении закрываются с пояснением и не применяются; предложение, созданное старой версией во время отката,
  после возврата на rc.1 тоже не применится — нужно подготовить новый предпросмотр.

**Откат облика (v2 → v1):** облик задаётся при сборке web. Соберите тот же коммит с другим тегом — пересоберётся
только web, остальные образы возьмутся из кэша — и переключитесь на него:

```bash
PPM_DESIGN_V2=0 ./ppm-build.sh --rev <тот же коммит> --release rc.1-v1
./ppm-deploy.sh --env-file .runtime/ppm.env release rc.1-v1
```

Данные и схема не меняются. Возврат — `... release rc.1`.

Запись в Git по умолчанию выключена: `PPM_GIT_WRITE_ENABLED=0`. Включать только после живой проверки.

Перед ротацией — `./ppm-backup.sh`. Значения генерируйте так: `openssl rand -hex 32`. После — новая копия
`ppm.env` в менеджер паролей.

| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |

| `LIVE_SERVER_SECRET_KEY`                       | новое значение → `up`                                                                                                                                                                                                          | нет                                                                                                                |

| `RABBITMQ_PASSWORD`                            | `./ppm-deploy.sh compose exec plane-mq rabbitmqctl change_password plane <новый>` (затем очистите историю shell) → `ppm.env` → `up`                                                                                            | короткий перезапуск                                                                                                |

### Смена root-учётки MinIO — процедура (⚠ в RC не отрепетирована)

> **Предупреждение.** Эта процедура в release candidate **не проверялась ни разу**. Root-учётка MinIO — единственная
> учётка хранилища: её используют API, фоновые задачи, `minio-init` и бэкапы. Ошибка = нет доступа ко всем файлам
> (вложения и Хранилище) до возврата старых значений. Выполнять только в окно обслуживания, только после свежего
> бэкапа и **сначала на учебной копии** (п. 11). Если что-то пошло не так — сразу шаг 7 (откат).

1. Свежая копия: `./ppm-backup.sh --env-file .runtime/ppm.env --output-dir /srv/ppm-backups`; убедитесь, что копия
   `ppm.env` со **старыми** значениями есть в менеджере паролей.
2. Репетиция на учебной копии: восстановите эту копию в проект `ppm-drill` (п. 11, «Учения»), выполните на нём шаги
   3–6 (в файле `.runtime/drill.env`) и проверьте скачивание файла через SSH-туннель. Только если всё прошло —
   продолжайте на боевом сервере; учебную копию затем удалите (`destroy`).
3. Новые значения (не показываются на экране, сразу в файл-черновик 600):
   ```bash
   umask 077; { echo "MINIO_ACCESS_KEY=ppm$(openssl rand -hex 10)"; echo "MINIO_SECRET_KEY=$(openssl rand -hex 32)"; } > .runtime/minio-new.txt
   ```
4. Замените две строки `MINIO_ACCESS_KEY=` и `MINIO_SECRET_KEY=` в `.runtime/ppm.env` строками из
   `.runtime/minio-new.txt` в текстовом редакторе (`ppm-env.sh set` секреты намеренно не меняет), удалите черновик
   (`rm .runtime/minio-new.txt`), проверьте: `./ppm-env.sh check .runtime/ppm.env` (права 600, формат).
5. `./ppm-deploy.sh --env-file .runtime/ppm.env up` — пересоздаёт `plane-minio` (новая root-учётка, те же данные в томе
   `minio_data`), `minio-init`, `api`, `worker`, `beat-worker`; в конце preflight `object_storage_io` должен быть `ok`
   (запись и чтение новой учёткой).
6. Проверка: скачать вложение Work Item и файл Хранилища, открыть предпросмотр; сделать бэкап
   (`ppm-backup.sh` — он ходит в MinIO новой учёткой). Сохраните новый `ppm.env` в менеджер паролей.
7. **Откат**, если `plane-minio` не становится `healthy`, preflight хранилища — `fail` или файлы не открываются:
   верните старые строки из менеджера паролей в `.runtime/ppm.env` и выполните `./ppm-deploy.sh --env-file
.runtime/ppm.env up`. Данные в томе при смене учётки не меняются; если и откат не помог — восстановление из
   копии шага 1 в новый проект (п. 11, «Авария»).

| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| Не собирается образ                                  | сеть к npm/PyPI/Alpine/GitHub; повторить `ppm-build.sh` (продолжит с кэша); Docker Hub — `PPM_DOCKERHUB_MIRROR=mirror.gcr.io`                                     |
| `claim-admin`: «уже создан»                          | администратор есть; забытый пароль — `./ppm-deploy.sh compose exec api python manage.py changepassword <e-mail>` (спросит новый пароль)                           |
| «Only the global administrator can create projects»  | п. 6, `ppm_global_admin grant`                                                                                                                                    |
| Холст «не в сети» у всех                             | маршрут `/ws/` в прокси и сервис `api`: `logs api`, `logs proxy`; при недоступном Redis realtime выключен, сохранение работает                                    |
| `ppm-restore.sh`: «cannot decrypt»                   | не та парольная фраза (или файл повреждён — сверьте `.sha256`); ничего не восстановлено                                                                           |
| `ppm-restore.sh`: «already has … tables/objects»     | цель не пустая — восстанавливайте в новый проект (п. 11); поверх данных скрипт не пишет                                                                           |
| Git-сервер (Forgejo): вход, push, SSH, токен, вебхук | п. 17.13                                                                                                                                                          |

Что видят пользователи при отказе зависимостей (проверено на репетиции):

| Отказ    | Пользователь                                                                                                                                            |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Redis    | новый вход невозможен (ошибка при входе); у вошедших работают доски, задачи, Хранилище, поиск; Холст «не в сети» (без совместного присутствия)          |

## 16. Известные ограничения комплекта RC

- **Content-Security-Policy не задан** (решение — после RC). Холст (tldraw) использует встроенные стили, `blob:`-воркеры
  и `data:`-изображения, предпросмотр PDF — iframe; политику, которая ничего из этого не ломает, нужно отдельно
  подобрать и прогнать по Холсту, Хранилищу и god-mode. Сейчас действуют: `nosniff`, `X-Frame-Options SAMEORIGIN`,
  `Referrer-Policy`, `Permissions-Policy`, HSTS; скачивания Хранилища отдаются с `Content-Security-Policy:
default-src 'none'; sandbox`; бакет закрытый, подписанные ссылки живут 5 минут.
- Журналы запросов без строки запроса и без заголовков: прокси (Caddy — маскирует параметры и удаляет cookie,
  ключи API, `Referer`, `Location`), `api` (путь без query, токен сброса пароля в пути маскируется), `web`/`admin`
  (nginx: путь без query, без `Referer`; ошибки уровня запроса не пишутся), `space` и `live` (путь без query, без
  заголовков). `worker` работает с уровнем WARNING: аргументы задач (в них токены писем) не пишутся. В журнале
  внешнего API в базе (`api_activity_logs`, только запросы с ключом API) значения параметров-учётных данных и
  заголовки `Cookie`/`Authorization`/`Referer` заменяются на `[redacted]`; тела запросов там хранятся — это журнал
  аудита upstream Plane. Флаг `--access-logfile -` в команде запуска API (upstream) фактически ничего не пишет:
  конфигурация логов Django отключает журнал uvicorn (проверено на стенде).
- `max_header_size 25MB` в Caddy унаследован от upstream Plane; тело запроса ограничено 16 МБ (прокси) и лимитом
  загрузок приложения.
- Отказ MinIO: загрузка в Хранилище ждёт ~10 с (всего 2 попытки клиента S3; настраивается `PPM_S3_*` в
  `ppm.env`). Задачи экспорта и команды создания бакета используют свои клиенты S3 без этих ограничений.
- Серверное чтение файла Хранилища в память ограничено: предпросмотр — 16 МБ, остальное — 250 МБ на файл.
- DRF 3.17.1 оставлен. Совет CVE-2026-73228 нейтрализован: upstream-middleware ограничивает тело запроса
  (413), прокси — 16 МБ. Совет CVE-2026-73229 касается `AdminRenderer`, PPM его не использует.
  Предупреждения `pnpm audit` у зависимостей upstream Plane — в отчёте RC-A.
- Мониторинга и алертов нет: проверки вручную по п. 14.
- Образы собираются на сервере, реестра образов нет. `apk upgrade` при сборке — сборки воспроизводимы по
  исходникам, базовым образам и `pip freeze`, но не побитово.
- Формат копий — `ppm-backup/3` (зашифрованный, с Git-сервером); копии `ppm-backup/2` (RC.1) восстанавливаются.
  Незашифрованные каталоги ранних репетиций RC этим скриптом не восстанавливаются.
- Git-сервер (Forgejo): свои учётные записи без единого входа (G2.2), права заводит администратор Forgejo; бэкап
  ненадолго останавливает Forgejo; миграция — только с GitHub; почты, CI и зеркал нет. Полный список — п. 17.12.
- Content-Security-Policy не задан и для `git.<домен>` (у Forgejo своя страница и свои правила фреймов).
- Смена root-учётки MinIO описана, но не отрепетирована (п. 13, процедура с предупреждением).
- Страница god-mode (upstream Plane) содержит ссылки на plane.so — используется только администратором.

## 17. Git-сервер (Forgejo)

Свой Git-сервер для кода команд: обычные `git clone`/`push`/`pull`, ветки и запросы на слияние (PR) на
`https://git.<домен>`. Это Forgejo 15 LTS — свободный аналог GitHub, установленный на этом же сервере. PPM подключает
его репозитории к проектам, видит коммиты и PR и связывает их с задачами по ключу (`ROBOT-12: …`).

Как устроено:

- Отдельное имя `git.<домен>` — свой origin: страницы Forgejo не работают «внутри» PPM. HTTPS — через тот же Caddy и
  в том же режиме (Let's Encrypt или локальный CA закрытой фазы), git по SSH — встроенный SSH-сервер Forgejo на порту
  `2222` (выключается, п. 17.11). Сам Forgejo (порт 3000) снаружи недоступен.
- База `forgejo` со своей ролью — в том же PostgreSQL; данные (репозитории, LFS, вложения, SSH-ключи сервера) — том
  `forgejo_data`; всё это — в тех же зашифрованных бэкапах (п. 17.10).
- Регистрации нет, без входа ничего не видно, новые репозитории и организации — приватные. Почта, проверка обновлений,
  зеркала, Actions (CI), реестр пакетов и федерация выключены; Forgejo ничего не запрашивает в интернете, вебхуки
  может отправлять только в PPM. Единственное исключение — перенос с GitHub, который администратор запускает сам
  (п. 17.7).
- Все настройки — в `ppm.env` и `docker-compose.git.yml` (переменные `FORGEJO__…`); веб-установщика нет, `app.ini`
  собирается заново при каждом запуске.
- PPM читает Forgejo служебной учётной записью `ppm-bot` с токеном **только на чтение**; писать в Forgejo PPM не может.

> **Администратор видит весь код.** Администраторы Forgejo (владелец и служебная учётная запись `ppm-bot`) видят все
> репозитории всех команд. Поэтому подключать репозитории Forgejo к проектам PPM может только глобальный администратор
> PPM (п. 17.8), а права администратора Forgejo давайте только тем, кому можно видеть весь код.

### 17.1 DNS, порты и файрвол

1. DNS: A-запись (и AAAA, если есть IPv6) `git.<домен>` → тот же IP, что у домена PPM. Проверка:
   `dig +short git.ppm.example.ru`. Без неё Let's Encrypt не выпустит сертификат для Git-сервера (п. 7).
2. HTTPS идёт через уже открытые 80/443. Для git по SSH откройте TCP `2222` (в облаке и `sudo ufw allow 2222/tcp`)
   к моменту открытия по домену (п. 7). Как и 80/443, порт `2222` слушает только `127.0.0.1`, пока
   `PPM_BIND_ADDRESS=127.0.0.1` (закрытая фаза).
3. Порт 22 сервера остаётся за SSH администратора, поэтому у git свой порт. Другой номер:
   `./ppm-env.sh set .runtime/ppm.env PPM_GIT_SSH_PORT 2022` → `./ppm-deploy.sh --env-file .runtime/ppm.env up`.

### 17.2 Включение

- **Новый сервер:** `ppm-env.sh init` (п. 4) уже пишет ключи Git-сервера (`PPM_GIT_*`, `PPM_FORGEJO_*`, секреты
  `FORGEJO_*`) — ничего делать не нужно; `up` (п. 5) запускает и Forgejo.
- **Обновление с RC.1:** в старом `ppm.env` этих ключей нет — `check` и `up` об этом напоминают, а Git-сервер до тех
  пор выключен. Добавьте ключи; остальные строки файла не меняются (ни одного байта):
  ```bash
  ./ppm-env.sh add-git .runtime/ppm.env
  ./ppm-deploy.sh --env-file .runtime/ppm.env up
  ```
  Затем сохраните новую копию `ppm.env` в менеджер паролей.
- `up` создаёт базу и роль `forgejo` (на существующем PostgreSQL — тоже; повторный запуск ничего не ломает),
  запускает Forgejo (первый запуск — 1–2 мин) и проверяет его изнутри сети и через `https://git.<домен>`: в выводе
  preflight появляются `git_internal`, `git_public` и `git_token`.

### 17.3 Первичная настройка (оператор)

```bash
./ppm-deploy.sh --env-file .runtime/ppm.env git-bootstrap
```

- Создаёт служебную учётную запись `ppm-bot` — администратора Forgejo (он должен видеть все репозитории). Пароля
  `ppm-bot` не знает никто: для своих шагов скрипт получает временный токен через командную строку Forgejo, а в конце
  ставит `ppm-bot` новый случайный пароль, который нигде не показывается и не сохраняется. Ни пароли, ни токены не
  появляются в командных строках процессов (их видно в `ps` на сервере) — только в каналах между программами.
- Создаёт системный вебхук (сразу для всех репозиториев) на приёмник PPM: подпись секретом
  `PPM_FORGEJO_WEBHOOK_SECRET`, события — push, запросы на слияние (открытие, изменение, новые коммиты, слияние,
  закрытие), создание и удаление веток и тегов, удаление репозитория.
- Выпускает новый токен PPM **только на чтение** (`read:repository`, `read:organization`, `read:user`), когда
  прежнего нет, он не работает или задан `--rotate-token`. Порядок безопасный: новый токен сначала записывается в
  `ppm.env` (`PPM_FORGEJO_TOKEN`, права 600), затем перезапускаются только `api`, `worker` и `beat-worker` и
  проверяется работа с ним — и только после этого отзываются прежние токены и временный токен `ppm-bot`. Если
  что-то сорвалось, сообщение говорит, какой токен сейчас в работе.

Команду можно повторять: она приводит всё к нужному виду, а рабочий токен оставляет прежним. Новый токен с отзывом
старого: `git-bootstrap --rotate-token`. **После выпуска нового токена сохраните новую копию `ppm.env` в менеджер
паролей.** Если Forgejo не запущен, команда сразу откажет и попросит сначала `up`.

### 17.4 Администратор Forgejo для владельца (владелец)

```bash
./ppm-deploy.sh --env-file .runtime/ppm.env git-admin --username <имя> --email <e-mail владельца>
```

- Создаётся администратор Forgejo со случайным **одноразовым** паролем (его придумывает сам Forgejo). Пароль пишется
  только в файл `.runtime/ppm/forgejo-admin-credentials.txt` (права 600), на экран — только путь к нему.
- **Первый вход — после открытия по домену (п. 7).** В закрытой фазе всё слушает только адрес `127.0.0.1` самого
  сервера, поэтому `https://git.<домен>/` с вашего компьютера ещё не откроется. Ждать открытия безопасно: регистрации
  нет, а пароль знает только владелец. Кто умеет, может войти и раньше — через SSH-туннель
  (`ssh -L 8443:127.0.0.1:443 <сервер>`) и строку `127.0.0.1 git.<домен>` в файле hosts своего компьютера, адрес
  `https://git.<домен>:8443/` (браузер предупредит о локальном сертификате закрытой фазы).
- Вход: имя и пароль из файла — Forgejo сразу попросит задать свой пароль (не короче 12 символов). Затем удалите файл:
  `rm .runtime/ppm/forgejo-admin-credentials.txt`.
- Сразу включите двухфакторную аутентификацию: аватар → «Настройки» → «Безопасность».
- Забыли пароль (почты у Git-сервера нет): та же команда с `--reset-password` — новый одноразовый пароль в тот же
  файл (он задаётся через API Forgejo, не через командную строку). Если учётная запись уже есть, команда без
  `--reset-password` откажет и подскажет это.
- Имя `ppm-bot` занято служебной учётной записью: не входите под ней, не меняйте и не лишайте прав администратора.

### 17.5 Люди, организации, команды и доступы (администратор Forgejo)

Регистрации нет — каждого человека заводит администратор (единый вход через PPM появится в G2.2):

1. **Люди:** аватар → «Панель управления» → слева «Идентификация и доступ» → «Пользователи» → «Создать новую уч.
   запись»: имя, e-mail, временный пароль; галочку «Требовать смену пароля пользователем (рекомендуется)» оставьте.
   Имя и временный пароль передайте человеку лично, не в общих чатах.
2. **Организация** — пространство команды или направления (например, `robotics`): «+» справа вверху → «Создать
   организацию» (откроется страница «Новая организация»), видимость «Частная». Обычные пользователи создавать
   организации не могут — только администратор.
3. **Команды и права** (организация → «Команды» → «Новая команда», например `developers`): «Доступ к репозиториям» —
   «Конкретные репозитории» (только то, что добавлено команде вручную) или «Все репозитории»; галочка «Создать
   репозитории» — если команда заводит их сама (в том числе через `git push`, п. 17.6). В «Разрешения» — «Административный
   доступ» (полный push/pull и управление составом команды) или «Настраиваемый доступ»: тогда права задаются **по
   разделам репозитория** отдельной таблицей («Код», «Задачи», «Слияния», «Выпуски», «Вики», «Проекты» и т. д.), у
   каждого раздела свой переключатель «Нет доступа / Чтение / Запись» — единого «Чтение/Запись/Администратор» на всю
   команду нет. Разработчикам обычно достаточно «Запись» у разделов «Код» и «Слияния». Затем «Добавить участника».
   Команда `Owners` — владельцы организации: полный доступ ко всем её репозиториям.
4. **Доступ к одному репозиторию** человеку вне команды: репозиторий → «Настройки» → «Соучастники» → «Добавить
   соучастника».
5. **Уход человека:** «Панель управления» → «Пользователи» → найдите человека → «Изменить» → отметьте галочку
   «Приостановленная уч. запись» (блокирует вход, историю и авторство коммитов сохраняет — это **не** снятие «Может
   входить», такого флажка в Forgejo 15 нет) → «Обновить учётную запись». На той же странице рядом — кнопка «Удалить
   учётную запись»: она стирает аккаунт безвозвратно, не перепутайте её с блокировкой.

Руководители проектов и разработчики видят только репозитории своих организаций и команд; администратор — все.

### 17.6 Быстрый старт разработчика

Этот пункт можно переслать разработчику целиком.

1. Войдите на `https://git.<домен>/` (имя и временный пароль — от администратора) и задайте свой пароль.
2. Доступ для git — один из двух способов:
   - **SSH-ключ** (удобнее): `ssh-keygen -t ed25519`, если ключа ещё нет; содержимое `~/.ssh/id_ed25519.pub` →
     аватар → «Настройки» → «Ключи SSH / GPG» → «Управление ключами SSH» → «Добавить ключ»;
   - **токен для HTTPS:** аватар → «Настройки» → «Приложения» → в разделе «Токены доступа» нажмите «Новый токен
     доступа» → на открывшейся форме «Создать новый токен» впишите имя, в «Выбрать разрешения» у строки `repository`
     поставьте «Чтение и запись» → «Создать токен». Токен показывается один раз: при `git push` по HTTPS вводите своё
     имя, а вместо пароля — токен (git запомнит его в системном хранилище паролей). ⚠ У уже выпущенного токена рядом
     в списке есть кнопка **«Создать новый»** — она не добавляет второй токен, а **заменяет** этот: старый сразу
     отзывается (диалог подтверждения так и предупреждает: «Замена токена доступа: будет создан новый токен,
     предыдущий будет отозван…»). Нажимайте её, только если сознательно хотите отозвать прежний токен.
3. Клонировать (адрес — на странице репозитория: переключатель «HTTPS» / «SSH» у поля адреса и кнопка копирования
   рядом с ним; отдельной кнопки «Клонировать» в Forgejo 15 нет):
   ```bash
   git clone ssh://git@git.<домен>:2222/<организация>/<репозиторий>.git    # по SSH
   git clone https://git.<домен>/<организация>/<репозиторий>.git           # по HTTPS
   ```
4. Новый репозиторий без веб-интерфейса — `git push` в ещё не существующий адрес: он создастся **приватным** (в
   организации — если у вашей команды есть право создавать репозитории):
   ```bash
   git remote add origin ssh://git@git.<домен>:2222/<организация>/<новый-репозиторий>.git
   git push -u origin main
   ```
5. Ключ задачи — в сообщении коммита, названии ветки или PR: `ROBOT-12: исправить датчик`. PPM свяжет их с задачей.
6. PR: отправьте ветку (`git push -u origin robot-12-sensor`) — Forgejo покажет ссылку на создание запроса на
   слияние (или вкладка «Слияния» → «Создать запрос»; «Новый запрос на слияние» — это только всплывающая подсказка у
   значка ветки, отдельного такого пункта меню нет). Обсуждение, ревью и слияние — в Forgejo.
7. VS Code: «Clone Git Repository…» с тем же адресом; вход — SSH-ключом или токеном, как выше.

### 17.7 Перенос репозиториев с GitHub

Встроенная миграция Forgejo переносит код, ветки и теги, а по выбору — задачи, PR, релизы и вики. Разрешён только
источник GitHub (`github.com`, его API и хранилище файлов); внутренние адреса сервера запрещены. **Запустить
миграцию может любой, кто может создавать репозитории** (свои или в организации): это исходящие запросы сервера на
GitHub. Когда перенос закончен, выключите миграции (шаг 5).

1. На GitHub: «Settings» → «Developer settings» → «Personal access tokens» → fine-grained токен с доступом на чтение
   к нужным репозиториям (Contents, Metadata, Issues, Pull requests — Read-only).
2. В Forgejo: «+» → «Выполнить перенос» (откроется страница с непереведённым заголовком «Migrate repository») →
   «GitHub»: адрес `https://github.com/<владелец>/<репозиторий>`, токен, владелец в Forgejo (организация), видимость
   «Приватный»; отметьте, что переносить.
3. Это разовый перенос: зеркалирование (постоянная синхронизация) выключено. После проверки команда работает с
   Forgejo, а репозиторий на GitHub можно заархивировать. Токен GitHub после переноса удалите.
4. Проект PPM, подключённый к GitHub, переключите на новый репозиторий (п. 17.8): отключение репозитория GitHub
   сохраняет историю и ссылки.
5. После переноса — миграции выключить (пункт «Выполнить перенос» пропадёт у всех), включить снова — значение `false`:
   ```bash
   ./ppm-env.sh set .runtime/ppm.env PPM_GIT_DISABLE_MIGRATIONS true
   ./ppm-deploy.sh --env-file .runtime/ppm.env up
   ```

### 17.8 Подключение репозитория к проекту PPM (глобальный администратор PPM)

Проект PPM → раздел «Код» → «Подключить с нашего Git-сервера» → выбрать репозиторий. Подключать и отключать
репозитории Forgejo может только глобальный администратор PPM: служебная учётная запись видит весь код, и выбор
репозитория не должен давать руководителю проекта доступ к чужому коду (ему показывается подсказка «Репозиторий
подключает администратор PPM»). Через минуту в «Коде» появляются ветки, коммиты и PR; дальше события приходят сразу
(вебхук). Если событие всё же пропущено (например, вебхук на время выключали), плановая сверка подтянет его сама не
позже чем через **15 минут**, а кнопка **«Обновить»** у подключения в «Коде» — сразу, без ожидания (п. 17.13). Команды
`git clone` — там же, «Как скачать код».

### 17.9 Обновление Forgejo

Forgejo обновляется отдельно от PPM — сменой digest образа в пределах ветки 15.x (LTS, поддержка до 2027-07-15):

1. Заметки о выпуске: https://codeberg.org/forgejo/forgejo/releases — нет ли особых шагов. Digest свежего образа
   `15-rootless`:
   ```bash
   docker buildx imagetools inspect codeberg.org/forgejo/forgejo:15-rootless | grep -m1 Digest
   ```
2. Бэкап (п. 10).
3. Переключение (PPM не перезапускается; Forgejo при старте сам обновит схему своей базы):
   ```bash
   ./ppm-env.sh set .runtime/ppm.env PPM_FORGEJO_IMAGE codeberg.org/forgejo/forgejo:15-rootless@sha256:<digest>
   ./ppm-deploy.sh --env-file .runtime/ppm.env up
   ```
4. Проверка: `preflight` — `git_internal`, `git_public`, `git_token` — `ok`; вход в Forgejo; `git clone`.

Откат на прежний digest работает, только если новая версия не меняла схему базы; иначе — восстановление копии шага 2
(п. 11). Переход на следующую LTS-ветку (16.x и дальше) — отдельное решение с репетицией на учебной копии.
Если codeberg.org недоступен, тот же образ отдаёт зеркало:
`data.forgejo.org/forgejo/forgejo:15-rootless@sha256:<тот же digest>` (так же в `PPM_FORGEJO_IMAGE`).

### 17.10 Бэкап и восстановление

- `ppm-backup.sh` (п. 10) кладёт в тот же зашифрованный архив дамп базы `forgejo` (с числом строк каждой таблицы) и
  данные Forgejo: репозитории, LFS, вложения, аватары и SSH-ключи сервера (без очередей, поисковых индексов, кэша
  архивов, сессий, журналов и временных файлов — они пересоздаются; без `app.ini` — он собирается из `ppm.env`).
  Если Git-сервер выключен (п. 17.11), а его база и данные остались на сервере, они всё равно попадают в копию.
- На время копирования Forgejo **останавливается** (секунды или минуты — по объёму кода): так база и репозитории в
  копии относятся к одному моменту. `git push` в эти секунды получает ошибку — достаточно повторить. Ночной cron
  (п. 10) делает паузу незаметной. После копии Forgejo запускается сам, даже если бэкап упал; если процесс бэкапа
  убили в эти секунды (`kill -9`, выключение питания), следующий бэкап сам запустит Forgejo и предупредит (или сразу:
  `./ppm-deploy.sh --env-file .runtime/ppm.env up`). Предупреждение «Forgejo was not running» значит, что Forgejo
  был остановлен до бэкапа — запустите его тем же `up`.
- В описи (`.manifest.json`) — раздел `git_server`: версия Forgejo, число репозиториев на диске и в базе,
  LFS-объектов и вложений.
- `ppm-restore.sh` (п. 11) восстанавливает базу `forgejo` (число строк каждой таблицы — как в дампе) и данные, затем
  сверяет: репозиториев на диске = записей в базе = как в копии, и проверяет `git fsck` пять случайных репозиториев
  (`PPM_RESTORE_FSCK_SAMPLE=<n>` — другое число). Копия учений (`--drill`) Git-сервера никуда не обращается: вебхуки
  и миграции уходят в закрытый локальный порт, миграции выключены.
- Архив с Git-сервером восстанавливается только туда, где он включён (иначе отказ ещё до запуска с подсказкой
  `ppm-env.sh add-git`). Архивы RC.1 (без Git-сервера) восстанавливаются как раньше; Forgejo цели стартует пустым.
- Авария (новый сервер, п. 11): `ppm.env` — из менеджера паролей, с тем же `FORGEJO_SECRET_KEY` (иначе людям придётся
  заново включать двухфакторную аутентификацию). После восстановления выполните `git-bootstrap`: он проверит токен и
  выпустит новый, если в сохранённой копии `ppm.env` его нет.
- Учебная копия со своим `ppm.env` получает другие секреты: вебхук и токен копии не совпадают с исходными — для
  учений это не нужно (или выполните на копии `git-bootstrap`).

### 17.11 Выключение SSH или всего Git-сервера

- **Только HTTPS:** `./ppm-env.sh set .runtime/ppm.env PPM_GIT_SSH_ENABLED 0` → `up`. Порт `2222` закрывается,
  Forgejo показывает только HTTPS-адреса. Включение — значение `1` и `up`.
- **Весь Git-сервер:** `./ppm-env.sh set .runtime/ppm.env PPM_GIT_SERVER_ENABLED 0` → `up`. Контейнер Forgejo
  удаляется, сайт `git.<домен>` отключается, у PPM пропадают `PPM_FORGEJO_*`: подключения Forgejo в разделе «Код»
  помечаются недоступными, история, ссылки и карточки остаются. **Данные не удаляются** — том `forgejo_data` и база
  `forgejo` сохраняются и **по-прежнему попадают в каждый бэкап**; включение — `1` и `up`. Удаление данных Forgejo —
  только отдельным решением владельца. Если после выключения бэкап пишет «WARNING: THE GIT SERVER IS NOT IN THIS
  BACKUP» — код в копию не попал (например, пропал образ Forgejo или осталась только часть данных): включите
  Git-сервер (`PPM_GIT_SERVER_ENABLED 1`, `up`) и сделайте бэкап снова.
- Прежде чем выключать, проверьте, что в копиях есть код (раздел `git_server` в `.manifest.json` последней копии).

### 17.12 Ограничения и безопасность

- Учётные записи Forgejo — свои, отдельно от PPM: единый вход через PPM и автоматические доступы по проектам — G2.2.
  Людей и права заводит администратор Forgejo (п. 17.5); ссылки на коммиты в отчётах — G2.3.
- Просмотр кода, diff, ревью и слияние PR — в Forgejo; PPM показывает метаданные и ведёт туда ссылками. Запись в Git
  из PPM (ветка и черновой PR) для Forgejo не делается.
- Выключены: регистрация, почта (пароль восстанавливает администратор или `git-admin --reset-password`), зеркала,
  Actions (CI), реестр пакетов, федерация, проверка обновлений, загрузка аватаров из интернета. Миграции с GitHub
  включены, пока идёт перенос (п. 17.7), и выключаются `PPM_GIT_DISABLE_MIGRATIONS=true`.
- Откат PPM на rc.1 отключает сайт `git.<домен>` до возврата на rc.2 (п. 12, `--allow-git-site-loss`).
- Один запрос к Git-серверу — не больше `PPM_GIT_MAX_BODY_SIZE` (1 ГБ): `git push` отправляет все новые объекты
  одним запросом, поэтому очень большой первый push разбейте на части (или поднимите лимит и сделайте `up`). Git LFS
  работает.
- Токены API принимаются только в заголовке `Authorization`; `?token=` в адресе отвергается — адреса попадают в
  журналы и историю браузера. Журнал запросов самого Forgejo выключен (он пишет адрес вместе со строкой запроса);
  запросы видны в журнале прокси без строки запроса и без заголовков с учётными данными, `scan-logs` проверяет и их.
- Бэкап ненадолго останавливает Forgejo (п. 17.10).
- Push-вебхук Forgejo несёт не больше 15 коммитов; остальные коммиты большого push PPM получает сверкой.
